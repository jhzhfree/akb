## 二、双周迭代节奏

```text
周一 需求澄清会（30 分钟）→ 周二 迭代规划（Story 拆分与估点）
→ 周三~下周二 开发与联调（每日站会 15 分钟）
→ 下周三 提测与回归 → 下周四 预发验证与压测
→ 下周四 21:00 发布评审 → 下周五 01:00 变更窗口发布
→ 下周五 迭代回顾与复盘
```

| 会议 | 频率 | 时长 | 参与人 | 产出 |
|---|---|---|---|---|
| 需求澄清 | 每两周 | 30 分钟 | 产品、研发、测试 | 需求澄清记录 |
| 迭代规划 | 每两周 | 90 分钟 | 全体 | Sprint Backlog |
| 每日站会 | 每日 | 15 分钟 | 研发、测试 | 阻塞项清单 |
| 发布评审 | 每两周 | 45 分钟 | 研发、测试、运维、产品 | 发布评审结论 |
| 迭代回顾 | 每两周 | 60 分钟 | 全体 | 改进项 |

## 三、分支与代码规范

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 主干，随时可发布 | 长期 |
| `release/*` | 发布分支 | 版本发布后归档 |
| `feature/*` | 功能分支 | 合并后删除 |
| `hotfix/*` | 紧急修复 | 修复后合并回 main 与 release |

- 提交规范：`<type>(<scope>): <subject>`，type 取 feat / fix / refactor / perf / docs / test / chore；
- PR 必须关联 Jira issue，至少 1 名同级评审通过，CI 全绿方可合并；
- 单次 PR 建议 ≤ 400 行改动，超过需在描述中说明拆分原因。

## 四、需求交付流程（Jira 状态流）

```text
待办(Backlog) → 已选择(Selected) → 开发中(In Progress) → 待评审(In Review)
→ 待测试(Ready for Test) → 测试中(In Test) → 待发布(Ready for Release)
→ 已完成(Done) / 已拒绝(Rejected)
```

- 状态流转须同步更新「剩余工时」与「完成百分比」；
- 阻塞超过 1 天的 issue 必须在站会提出并指定协助人；
- 需求变更须由产品经理在 Jira 更新验收标准，并重新估点。

## 五、缺陷管理

| 优先级 | 定义 | 修复时限 |
|---|---|---|
| P0（Blocker） | 生产不可用、资金损失 | 立即（2 小时内止损） |
| P1（Critical） | 核心功能不可用 | 24 小时 |
| P2（Major） | 功能降级，有绕行方案 | 本迭代内 |
| P3（Minor） | 体验问题、非核心缺陷 | 下迭代或排期 |

缺陷单须包含：环境、复现步骤、期望与实际结果、日志/traceId、影响面。

## 六、文档与知识沉淀

- 设计方案写 Confluence（空间 KOS-RND），模板见《Confluence 文档规范》；
- 故障复盘、发布记录、接口变更须在 3 个工作日内沉淀；
- 每个迭代至少产出 1 篇技术文档，计入团队「知识贡献」考核；
- 文档上传后同步至公司知识平台，作为知识库数据源。

## 七、跨团队协作

| 场景 | 对接方式 |
|---|---|
| 生产发布 | 提前 1 天在 ITSM 提交变更单，运维值班台审批 |
| 生产权限 | OA 提申请，信息安全部与运维值班台审批 |
| 数据修复 | DBA 评审 + 变更单，禁止直连生产执行写操作 |
| 安全评审 | 涉及鉴权、资金、数据外发的方案须安全前置评审 |
| 客户问题 | 客户成功部转 Jira，研发标注客户影响与 SLA |
