## 操作背景与问题描述

**问题描述**：订单服务的 `/data/app/order` 目录及其子目录权限被全域开放为 777，任何本地账号均可写入应用脚本，属于权限提升类风险敞口。

**操作起因**：订单应用启动时报 Permission denied，操作人为快速恢复业务直接使用递归 chmod 放开权限，未按排障流程先核对属主与 umask。

**审计发现的违规点**：该次操作没有会话工单，且 `app` 资源账号持有 sudo 到 root 的权限，违反了账号与授权管理规范中「应用账号不得具备 sudo 到 root 权限」的要求。

## 命中策略与处置动作

- 命中命令：`chmod -R 777 /data/app/order`，命令策略命中 L2 审批级（递归全域开放），操作人没有会话工单，会话被暂停等待审批 15 分钟后仍由 sudo 直接执行成功，说明 sudo 通道绕过了命令拦截。
- 未形成 L1 的原因：本机 sudo 提权路径未在堡垒主机侧做命令策略映射，命令策略只对堡垒主机通道生效。
- 处置动作：15:52 安全审计员陈静发起二级告警；16:10 运维主管王强回收 `app` 账号的 sudo 权限。
- 恢复动作：将目录权限恢复为 755、`start.sh` 恢复为 750，并将属主改回 `order:order`。

## 影响范围

- 受影响对象：`/data/app/order` 目录下 412 个文件与 38 个子目录的权限位。
- 业务影响：无中断，但存在任意本地账号可篡改启动脚本的权限敞口，敞口存在时长 35 分钟。
- 数据影响：无数据删除或篡改，已通过文件完整性校验确认。

## 处理结论与复盘改进

**合规结论**：属违规操作。缺少会话工单，且使用了未被授权的 sudo 提权能力。

**复盘改进项**：

1. 回收全部生产主机上 `app` 账号的 sudo 权限，sudo 授权改为命令白名单，责任人：张伟，闭环时限 2026-08-16。
2. 将 `chmod -R 777` 类递归全域开放命令提升到 L1 禁止级，责任人：陈静，闭环时限 2026-08-10。
3. 在排障手册中补充「Permission denied 的正确排障步骤」，先核对属主与 umask，禁止直接用 777 兜底，责任人：赵鹏，闭环时限 2026-08-20。
