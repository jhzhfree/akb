# 发布变更与回滚管理规范

> 文件编号：OPS-RULE-08　|　版本：V2.6　|　生效日期：2026-04-01　|　有效期至：2027-03-31
> 归口部门：运维部（SRE 组）　|　审批人：王强（E10087）

## 一、变更分类

| 类型 | 说明 | 审批链 | 窗口 |
|---|---|---|---|
| 标准变更 | 已验证过的常规发布、配置调整 | 值班台登记 | 工作日 09:00–21:00 |
| 常规变更 | 新版本发布、参数调整、扩容 | 主管 + 值班台 | 周二/周四 01:00–05:00 |
| 重大变更 | 架构调整、数据迁移、跨版本升级 | 主管 + 运维总监 + 业务负责人 | 周六 00:00–06:00 |
| 紧急变更 | 故障止损、安全补丁 | 值班台口头授权，事后 30 分钟补单 | 随时 |

## 二、发布流程（六步）

```text
Step 1 变更单：ITSM 提交，写明变更内容、影响面、回滚方案、验证方法
Step 2 预发验证：预发环境全量回归，性能不低于现网 95%
Step 3 灰度发布：5% → 30% → 100%，每档观察 15 分钟
Step 4 指标观察：错误率、P99、CPU、慢查询、业务核心指标
Step 5 全量或回滚：指标异常立即回滚，不得「观察看看」
Step 6 变更闭环：单内填写实际结果、耗时与遗留项，24 小时内闭环
```

## 三、灰度与观察指标

灰度期间必须同时观察以下指标，任一超标即停止放量：

| 指标 | 阈值 | 来源 |
|---|---|---|
| 接口错误率 | > 0.5% 或较基线翻倍 | APM / Prometheus |
| P99 延迟 | > 基线 1.5 倍 | APM |
| 慢 SQL 数量 | 新增 > 5 条/分钟 | DB-Audit |
| GC 次数（JVM） | Full GC > 3 次/分钟 | JMX |
| 业务核心指标（支付成功率） | 下降 > 0.3% | 业务看板 |

## 四、回滚标准与操作

出现下列任一情况**立即回滚**，不需要额外审批：

1. 发布后 10 分钟内错误率超过 1%；
2. 核心接口 P99 超过基线 2 倍；
3. 出现数据不一致、资金类异常；
4. 回滚依赖的上一版本镜像不可用以外的任何异常。

```bash
# K8s 回滚（支付服务）
kubectl -n payment rollout undo deploy/pay-api
kubectl -n payment rollout status deploy/pay-api --timeout=300s

# 物理机/虚机回滚：切回上一版本软链
ln -sfn /data/apps/pay-api-v2.8.2 /data/apps/pay-api-current
systemctl restart pay-api
```

## 五、发布窗口与冻结期

- 常规窗口：周二、周四 01:00–05:00；
- **发布冻结期**：每月最后 3 个工作日（结算期）、大促前 7 天至大促结束；
- 冻结期内仅允许紧急变更（故障止损与安全补丁），且需运维总监审批。

## 六、变更记录与审计

每次变更在 ITSM 留存：变更单号、申请人、审批人、变更内容、执行时间、观察结果、回滚记录。所有生产变更操作通过堡垒主机执行，命令序列自动进入 KosAudit 审计留存 180 天。

| 字段 | 示例 |
|---|---|
| 变更单号 | CHG-2026-08-0087 |
| 申请人 | 赵鹏（应用负责人，E10258） |
| 变更内容 | 支付服务 v2.8.3 灰度发布（30% → 100%） |
| 执行时间 | 2026-08-12 16:10–17:25 |
| 观察结果 | 错误率 0.12%，P99 340ms，符合预期 |
| 回滚记录 | 无 |

## 七、违规处理

- 未开变更单直接改生产配置：一级违规；
- 跳过预发验证直接上生产：二级违规；
- 发布后不观察直接下班：二级违规，造成故障的升级为一级。
