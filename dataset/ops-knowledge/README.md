# 场景数据集 1 · 运维知识库

> 场景定位：企业 IT 运维团队的统一知识库，覆盖**运维规范 + 操作手册 + 命令操作记录 + 故障与拦截事件 + FAQ + 月报复盘 + 口径通知**七类内容，模拟一个约 120 台主机、40+ 服务、8 人值班团队的真实运维知识规模。
> 虚构主体：蓝湖科技（CloudLake）运维部，与「公司制度」「工程协同」共用同一主体，便于跨场景实体关联（工号、主机名、工单号互通）。

## 二、刻意设计的「真实场景特征」

| 特征 | 设计 | 用途 |
|---|---|---|
| 口径冲突 | 09（5 分钟）与 18（3 分钟）对 P1 首响时限不一致，18 明确「以通知为准」 | 验证冲突裁决与版本化断言 |
| 同一事件的三种视角 | 8·12 故障同时出现在 13（操作记录）、16（复盘）、17（月报） | 验证多跳检索与证据聚合 |
| 命令与风险并存 | 04/05/06/07 给出大量命令，03 明确哪些是 L1/L2 | 验证答案门控不会「教人执行高危命令」 |
| 精确编号密集 | 工号 E10231、主机 srv-pay-01、归档 AUD-2026-08-12-00631、工单 ITSM-2026-08-0881 | 验证 BM25 精确召回 |
| 人员属性差异 | 张伟（内部）、刘洋（外包）、孙浩（厂商）权限不同 | 验证实体属性与权限语义 |

## 四、检索策略（已创建）

「运维知识库」策略要点：BM25 权重 1.30、卡片 1.25（命令与编号精确召回）；冲突类问题优先 claim 通道；时效权重 0.15、权威 0.20；`minRecallCandidates=30`；`faithfulnessMin=0.06`（运维答案必须给证据与命令出处）。定义文件：`../_scenarios/ops-knowledge.profile.json`。

## 五、导入与验证

```bash
# 导入本场景（含 schema 与检索策略）
python3 scripts/build-scenario-kbs.py --scenario ops --token <token>
```

验证建议（控制台「知识检索 → 搜索」）：

1. `rm -rf / 属于几级命令` → 应命中 03，答 L1 并说明拦截与双签；
2. `P1 首响时限是多久` → 应同时给出 09 的 5 分钟与 18 的 3 分钟，并说明以 9 月通知为准；
3. `8 月 12 日支付故障的原因` → 应聚合 13/16/17 三处证据，给出慢 SQL 与时间线；
4. `db-mysql-02 主从延迟 42s 怎么处理` → 应命中 12 与 05，给出 kill 审批与后续改进。
