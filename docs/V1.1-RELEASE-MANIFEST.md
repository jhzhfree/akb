>

> - `docs/V1.1-RELEASE-NOTES.md`：**功能发布说明**（做什么、每项验收标准、约束、下一版本方向），对客户/管理层口径

>
> 统计基准：产品版本 **1.1.0**（仓库 `v1.2` 开发分支现状）—— 后端 3 个 Controller / 61 个 HTTP 端点，AI 服务 30 个端点，前端 26 个 Vue 组件 / 11 个工作台页签，数据库 Flyway 迁移 V1—V25。

## 1. 版本标识与技术栈

### 1.1 版本

| 项 | 值 | 说明 |
|---|---|---|
| 产品版本 | **1.1.0** | 首个可对外交付的产品版本（代码、镜像、交付包统一使用该版本号） |
| 镜像标签 | `knowledge-os/{ai-service,backend,frontend}:1.1.0` | 由 `Makefile` 的 `VERSION ?= 1.1.0` 决定，与产品版本一致 |
| 前端包版本 | `knowledge-os-frontend@1.1.0` | `frontend/package.json` |
| AI 服务版本 | `1.1.0` | `ai-service/app/main.py`（FastAPI `version`） |
| 后端包版本 | `com.jh:knowledge-os-backend:1.1.0` | `backend/pom.xml` |
| 数据库 Schema | Flyway `V1` — `V25` | 后端启动自动迁移，禁止手工改表 |
| 交付包 | `ai-knowledge-1.1.0.tar.gz` | `scripts/package-release.sh` / `make package` 产物 |

> **版本一致性要求**：发版时以上四处必须同为 `1.1.0`（`Makefile` 的 `VERSION`、`frontend/package.json`、`ai-service/app/main.py`、`backend/pom.xml`）。升级或打补丁时按语义化版本递增，并在包内 `release.env` 中记录版本号与镜像前缀，用于安装与回退核对。

## 2. 功能清单（含实现程度与限制）

### 2.1 实现程度分级

| 标记 | 级别 | 含义 |
|---|---|---|
| ✅ | L4 完整 | 端到端闭环，界面 / 接口 / 数据齐全，有验收脚本覆盖 |
| ◐ | L3 可用-受限 | 功能可用，但存在明确边界（规模、算法精度、覆盖范围） |
| ⚠ | L2 后端就绪·前端未接 | 接口与数据完备，界面无入口，需走 API 或运维操作 |
| ✳ | L1 实验性 | 默认关闭或依赖外部组件，未纳入默认交付路径 |
| — | L0 未提供 | V1.1 不做 |

## 3. V1.1 全局限制（交付必须告知）

| # | 限制 | 影响 | 规避方式 |
|---|---|---|---|
| L-1 | **无内置身份认证**：依赖内网部署 + 网关鉴权；运维令牌仅覆盖索引写接口 | 无法区分操作者，审计主体不完整 | 前置反向代理注入身份头；S1 前确定认证方案（见 FEATURE-SCOPE Q1） |
| L-2 | **知识对象只做状态退役，不做物理删除** | 磁盘只增不减 | 靠生命周期治理（EXPIRED/SUPERSEDED）保证检索面干净；确需清理走运维脚本 + 审计 |
| L-3 | **答案门禁为词面算法**（中文 bigram + 否定词典），非 NLI 模型 | 改写句/长句可能被低估，个别句子被误判 CONTRADICTED | 已通过 claim 级降级保证「宁可少答，不可错答」；误判表现为答案少一句，不会静默出错 |
| L-4 | **ai-service 为单实例**，未启用 ES/Milvus 时索引落在本地卷 `ai_data` | 不可水平扩展，实例重建依赖卷恢复 | 生产规模建议启用 ES + Milvus；单实例场景必须做卷备份 |
| L-5 | **Reranker 默认关闭** | 排序质量依赖融合策略 | 需重排序时在镜像中加装 `torch`/`transformers` 并置 `RERANKER_ENABLED=true` |
| L-6 | **单租户、多知识库**，无跨库联邦、无库级配额与限流 | 多团队共享一套实例 | 按知识库隔离 + 网关侧限流 |
| L-7 | **无内置定时调度**：过期扫描、备份、索引巡检均需外部触发 | 治理动作依赖运维 | 由 crontab / K8s CronJob / 外部调度器调用既有接口 |
| L-8 | **规模承诺需压测确认**：建议先按 ≤5 万文档、≤500 万向量、20 并发问答对外承诺 | 超规模性能未验证 | 用 `performance/` 基线 + `scripts/release-qualification-benchmark.py` 实测后再调整承诺 |
| L-9 | 抽取与改写质量**强依赖所选 LLM**，换模型需回归 | 效果波动 | 换模型后执行 `scripts/release-quality-eval.py` 与种子集回归 |
| L-10 | 上传单文件 **100MB**，仅 PDF/Word/Markdown/文本（`.pdf`/`.docx`/`.md`/`.txt`） | 扫描件、PPT、Excel、HTML 无法接入 | 先转 PDF（带文本层）、Markdown 或纯文本再上传 |

## 4. 部署方式

V1.1 提供三种部署形态，按场景选择。

### 4.1 方式 A：离线安装包（生产推荐，默认交付形态）

适用：客户内网、无外网镜像仓库。

```bash
tar -xzf ai-knowledge-os-<VERSION>.tar.gz
cd ai-knowledge-os-<VERSION>
./install.sh          # 环境预检 + docker load 镜像 + 生成 .env
vi .env               # 修改全部 CHANGE_ME 占位值与模型地址
./start.sh            # 启动全部服务
./status.sh           # 查看容器状态与健康端点
```

- 预检要求：**Docker 20.10+**、docker compose v2 插件、目标机可解析镜像（离线包已内置全部镜像）
- 数据存放于命名卷（`mysql_data`、`neo4j_data`、`milvus_data`、`elasticsearch_data`、`ai_data` 等），项目名固定 `knowledge-os`，`./stop.sh` 不丢数据
- 默认访问地址：前端 `:8088`、后端 `:8080`（Swagger `/swagger-ui.html`）、Prometheus `:9090`、Grafana `:3000`

### 4.2 方式 B：容器编排（开发/演示/可联网环境）

```bash
make prod-env         # 由 .env.production.example 生成 .env.production
make prod-up          # docker compose -f deploy/docker-compose.prod.yml up -d --build
make prod-logs
```

服务组成：`mysql` / `redis` / `elasticsearch` / `milvus`（+`milvus-etcd`+`milvus-minio`）/ `neo4j` / `ai-service` / `backend` / `index-worker`（8081，仅跑 Outbox 投喂）/ `frontend` / `prometheus`。

关键部署约束：
- `backend` 与 `index-worker` 是**同一镜像的两个实例**，通过 `INDEX_OUTBOX_ENABLED` 区分；Outbox 投喂**只能有一个实例开启**，否则重复投递
- `ai-service` 单实例持有 `ai_data` 卷，不可扩副本（见 L-4）
- `STARTUP_FAIL_FAST=true` 时依赖不可用即退出，便于编排层发现问题

### 4.3 方式 C：源码裸跑（开发/二次开发）

```bash
make dev-install      # 创建 conda 环境 llmkb + 安装依赖
make dev-ai           # ai-service:12000（Ollama + 本地 BM25/向量 + Neo4j）
make dev-backend      # backend:8080（mvn spring-boot:run，JDK 8）
make dev-frontend     # frontend:5173（Vite，/api 代理到 8080）
make dev-all          # 三者并行
```

### 4.4 关键配置项

| 变量 | 说明 | 备注 |
|---|---|---|
| `LLM_PROVIDER` / `LLM_BASE_URL` / `LLM_MODEL` | 生成模型 | 默认 `ollama` + `qwen2.5:7b`；容器内访问宿主模型用 `http://host.docker.internal:11434` |
| `EMBEDDING_PROVIDER` / `EMBEDDING_MODEL` / `EMBEDDING_DIM` | 向量模型 | `nomic-embed-text` 为 **768**；维度与模型不一致会导致检索异常 |
| `RETRIEVAL_MODE` | 检索模式 | `auto`：ES/Milvus 可用则用之，否则降级本地 |
| `ELASTICSEARCH_ENABLED` / `MILVUS_ENABLED` | 外部检索设施开关 | 关闭时本地索引，仅适合单机小规模 |
| `RERANKER_ENABLED` | 重排序 | 默认 `false`，开启需镜像内含 torch |
| `GRAPH_PROVIDER` | 图存储 | 默认 `neo4j` |
| `*_HTTP_PORT` | 对外端口 | `PUBLIC_HTTP_PORT`（前端，默认 8088）、`BACKEND_HTTP_PORT`、`PROMETHEUS_HTTP_PORT`、`GRAFANA_HTTP_PORT` |

## 5. 升级包类型

V1.1 定义 5 类升级包，按变更范围选择，**不得跨类型混用**。

| 类型 | 编号 | 内容 | 适用场景 | 是否需停服 | 回滚方式 |
|---|---|---|---|---|---|
| **A. 全量离线包** | FULL | 3 个应用镜像 + 全部中间件镜像 + compose + 脚本 + monitoring | 首次部署、跨中间件版本升级、离线环境 | 是 | 保留旧包目录，回退启动旧包 |
| **B. 应用增量包** | APP-ONLY | 仅 `ai-service`/`backend`/`frontend` 镜像 + compose + 脚本（`INCLUDE_MIDDLEWARE=0`） | 小版本 / 补丁（无中间件变更） | 是（滚动替换镜像） | 镜像标签回退到上一版本 |
| **C. 数据库迁移** | DDL | Flyway `Vxx__*.sql`，**内置于 backend 镜像**，启动自动执行 | 随 A/B 自动进行，无需单独交付 | 由 A/B 决定 | V1.1 只做向后兼容 DDL（加表/加列/加索引），**不回滚 DDL** |
| **D. 索引重建包** | INDEX | 蓝绿 schema 发布 + Outbox 全量重放（`/index/schema/{kb}/rebuild` → `/activate/{releaseId}`） | **更换 Embedding provider/维度**、检索契约变更、漂移修复 | 否（蓝绿在线） | `/index/schema/{kb}/rollback/{releaseId}` |
| **E. 配置包** | CONF | `.env` 差异 + `monitoring/` 规则 | 端口、模型地址、告警阈值调整 | 否（restart 生效） | 还原 `.env` 备份 |

### 5.1 打包命令

```bash
# 全量离线包：dist/ai-knowledge-<VERSION>.tar.gz
VERSION=1.1.0 IMAGE_PREFIX=registry.example.com/knowledge-os make package

# 应用增量包（目标机可联网拉中间件）
INCLUDE_MIDDLEWARE=0 VERSION=1.0.1 ./scripts/package-release.sh

# 仅构建并推送镜像
make release-build VERSION=1.1.0 && make release-push VERSION=1.1.0
```

包内 `release.env` 记录版本号与镜像前缀，用于安装与回退核对。

### 5.2 标准升级流程（A / B 类）

1. **备份**：MySQL 逻辑备份 + 命名卷快照（`mysql_data`、`ai_data`、`neo4j_data`），记录当前镜像标签
2. **停服**：`./stop.sh`（保留数据卷）
3. **部署新包**：解压新版本目录 → `./install.sh` → 对比并合并 `.env`（**不要直接用新 `.env` 覆盖**，会丢失模型地址等已配值）
4. **启动与就绪**：`./start.sh` → `scripts/wait-ready.sh`
5. **验证**：
   - `./scripts/check-v11.sh`（44 项门禁）
   - `python3 scripts/release-go-no-go.py`
   - 抽查一条既有问答，确认引用与溯源正常
   - `GET /api/knowledge/index/drift/{kb}` 漂移为 0
6. **按需索引重建**：若本次涉及 embedding / 检索契约变更，执行 D 类（蓝绿重建 + 激活）

### 5.3 升级红线

- **禁止**在不停服情况下跨版本替换 `backend` 与 `index-worker`：两实例 Flyway 与 Outbox 会争抢
- **禁止**手工执行 `Vxx` SQL 或修改已应用的迁移文件
- 更换 Embedding 后**必须**执行 D 类重建，否则向量空间与索引不一致（表现为检索漂移/召回骤降）
- Grafana 默认口令 `admin/admin123` 上线前必须修改

## 7. 发布门禁与验收

| 阶段 | 门禁 | 命令 / 依据 |
|---|---|---|
| 构建前 | 44 项工程门禁（语法、契约、迁移、索引、RBAC…） | `./scripts/check-v11.sh` |
| 构建后 | 发布资格（质量/性能/一致性/故障注入） | `scripts/release-qualification-live.py`、`release-fault-injection.sh`、`release-blue-green-live.py`、`release-consistency-live.py` |
| 部署后 | 端到端闭环 | `python3 scripts/e2e-test.py` |
| 发布前 | Go / No-Go | `python3 scripts/release-go-no-go.py` + `GO-NO-GO-CHECKLIST.md` |

### 7.1 V1.1 出口标准

1. 端到端闭环：新环境 30 分钟内完成 上传 → 抽取 → 裁决 → 发布 → 提问 → 追溯到原文，无需调接口或改库
2. 证据可追溯：任一条答案引用可下钻至 ContentUnit 原文，无断裂
3. 无证据不结论：无相关知识时必须拒答或声明证据不足
4. 发布可回滚：完成一次蓝绿重建 + 回滚演练，回滚后问答结果一致
5. 权限不越界：无权限用户答案中不出现无权证据
6. 稳定性：Outbox 死信 0、索引漂移 0、72 小时无 OOM 与任务堆积
7. 文档齐备：部署手册、备份恢复演练记录、Go/No-Go 清单、发版清单（本文档）均已交付
