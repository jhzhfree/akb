# AKB 企业知识库地图与知识体系说明

> 本文是 AKB（AI 原生企业知识库平台）的全局知识地图，帮助产品、研发、实施和运维人员理解：平台中的“知识”是什么、知识如何从原始资料变成可治理和可检索对象、各服务如何协作，以及遇到问题时应从哪里查起。
>
> **代码基线**：`feature/octop-mcp-integration`，提交 `aedbcbdd34f9fb942947b4265b4e499368df66fa`（2026-10-25 核对）。本文描述该分支可见的架构与产品能力；历史方案和归档记录仅作背景。接口和配置细节以代码、OpenAPI 及当前部署配置为准。

## 1. AKB 是什么

AKB 是面向企业资料的知识生产、治理、检索和对外服务平台。它不是单纯的文件盘，也不是把文档片段直接交给大模型的聊天壳。平台围绕可信知识形成完整链路：

1. 收集知识库中的资料和外部来源；
2. 解析文档，保留版本、片段和证据位置；
3. 从证据中抽取卡片、断言、实体及关系；
4. 通过规则、AI 辅助和人工操作治理知识及冲突；
5. 将权威知识同步到文本、向量和图谱检索视图；
6. 检索时检查知识状态、用户权限和证据来源；
7. 返回可追溯的答案、候选、引用和查询轨迹；
8. 通过运营指标、事件、索引重建和补偿机制维护长期一致性。

核心架构原则是：**MySQL 保存权威业务状态；Elasticsearch、Milvus、Neo4j 及本地 fallback 保存可重建的检索视图。** 检索索引可以重建，原始资料、证据、审核状态、授权和业务审计必须以权威数据为准。

## 2. 一张全局知识地图

```text
知识来源
  └─ Source → SourceVersion → Document → DocumentRevision
       └─ ContentUnit（可检索片段）→ Evidence（可核验原文及位置）
            └─ KnowledgeCard / Claim
                 ├─ Entity / Alias / Relation（知识图谱）
                 ├─ Conflict / GovernanceDecision / Lifecycle
                 └─ DerivedKnowledge（从已有知识派生，保留依赖）

MySQL 权威数据
  ├─ 状态、版本、证据、权限、审核、审计、任务、发布记录
  └─ Transactional Outbox
       └─ Index Worker → Python AI Service → ES / Milvus / Neo4j

用户或外部 Agent
  └─ ACL + 状态过滤 → 多路召回 → 加权 RRF → 重排 → 上下文组装
       └─ 答案资格判定 → LLM（需要生成时）→ 引用 / Trace / 审计
```

这张图里几种“知识”不能混为一谈：

| 对象 | 回答的问题 | 主要作用 |
|---|---|---|
| Source / Document | 信息从哪里来？ | 记录来源、文件、修订和处理状态 |
| ContentUnit | 原文按什么粒度被检索？ | 提供文档片段召回和上下文候选 |
| Evidence | 哪段原文支持这个结论？ | 支持核验、引用、审计和追溯 |
| KnowledgeCard | 一项可供业务理解的主题知识是什么？ | 聚合主题内容、语义和证据 |
| Claim | 可验证的具体断言是什么？ | 支持状态裁决、冲突检测和细粒度检索 |
| Entity / Relation | 知识涉及哪些对象，它们如何关联？ | 支持实体统一、关系查询和图谱路径 |
| DerivedKnowledge | 由哪些已有知识推导而来？ | 表达派生结果及其依赖、失效传播 |
| QueryTrace / Citation | 某次回答用了什么？ | 重放、排障、评测和解释来源 |

## 3. 权威数据与派生视图

### 3.1 MySQL 是权威源

Java Backend 是业务权威状态的主要写入者，负责事务、权限、知识治理、API、任务编排及发布。MySQL 记录知识对象本身、证据关系、状态和版本、用户与 API Key 授权、审计、Outbox、后处理阶段及索引发布元数据。

资料解析和模型调用属于较慢的外部工作，通常安排在数据库事务外执行。随后使用短事务一次性提交本地业务状态和需要异步处理的任务。这样既不让远程调用长期占用数据库事务，也能在索引服务暂时不可用时保留已提交的权威知识。

### 3.2 搜索引擎是可重建视图

| 存储 | 主要用途 | 权威性 |
|---|---|---|
| Elasticsearch | BM25 全文搜索、结构化过滤和文本候选召回 | 派生视图 |
| Milvus | 文本向量近邻搜索 | 派生视图 |
| Neo4j | 实体、卡片、断言及关系图谱查询 | 派生视图；图结构的业务事实仍受权威数据约束 |
| Local JSON / 本地索引快照 | 开发、无外部引擎时的 fallback 或恢复路径 | 派生视图，不是生产主引擎 |

“最终一致”表示数据库提交和索引投递分开进行，短时间内可能出现索引滞后；它不表示可以忽略状态和权限差异。知识 UI、正式检索及索引运维应显式表达“权威记录已保存，但检索视图尚未就绪”的状态。

## 4. 知识对象与概念

### 4.1 知识库与场景

知识库是资料、知识对象、授权和检索配置的主要隔离边界。外部 API 可使用数据库 ID 或稳定的知识库编码；新集成优先使用稳定编码。每个知识库可以选择场景模板（代码中包括 `GENERAL`、`OPS`、`POLICY`、`BUSINESS`、`VULN`），模板提供切片、抽取、检索和回答等默认 profile，再由知识库配置覆盖。

场景模板决定默认行为，不应被当成 ACL。它不能替代用户权限、API Key scope、知识库绑定或知识对象上的访问标签。

### 4.2 来源、文档与修订

- **Source** 表示信息来源或接入渠道，可关联多个文档。
- **SourceVersion** 保存来源自身的版本线索或同步快照。
- **Document** 表示平台管理的一份资料。
- **DocumentRevision** 表示文档内容的一个修订版本。新版本通过 supersede 关系取代旧版本，使历史内容可追溯。
- 文档状态还反映解析、抽取、索引和后处理是否完成；文档入库成功不等于它的知识已审核，也不等于所有检索索引已就绪。

来源和文档回答“从哪里来”；Revision 回答“当时采用了哪一版”。同一份文件更新后，旧证据不应悄悄指向新正文。

### 4.3 ContentUnit 与 Evidence

- **ContentUnit（CU）** 是按配置策略切分出的可处理、可召回文本单元，可能带标题、页码、段落、表格、章节等定位信息。
- **Evidence（EVD）** 是能够定位回资料版本的原文证据，通常指向文档修订和内容单元，并保存文本锚点或来源位置。

ContentUnit 是处理和检索的粒度；Evidence 是对主张进行核验的依据。检索到某个段落并不自动证明某个抽取结论正确，证据存在也不代表它在语义上充分支持结论。

### 4.4 KnowledgeCard 与 Claim

- **KnowledgeCard（KC）**：围绕主题、实体或业务事项组织的知识表达，适合向用户展示和作为综合检索对象。
- **Claim（CLM）**：能够单独核验的事实或规则断言，适合细粒度审核、冲突检测、生命周期更新和精准召回。
- 卡片和断言均应通过证据关系回到源文档；对于缺少证据或证据不充分的对象，应进入治理或待审路径。
- 抽取产出默认直接置为 `APPROVED`（宽松口径，`knowledge.extraction.approval-mode=strict` 可切回“仅确定性来源自动批准”）。“确定性”标记只是候选来源提示，不构成批准凭据：宽松模式下知识先入库，状态可随时由人工改回 `UNCERTAIN` 或 `REJECTED`，治理痕迹完整保留。

### 4.5 Entity、Alias 与 Relation

- **Entity** 表示人员、组织、产品、流程、地点等被提及的现实或业务对象。
- **Alias** 保存实体名称、简称、历史名及其他写法，帮助跨文档归一。
- **Relation** 表示实体与实体、实体与知识对象之间的有类型关系。
- 实体消歧用于判断不同提及是否指向同一实体；错误合并会扩大错误关系传播范围，因此合并应保留来源依据、审计和可纠正路径。
- Neo4j 是查询图的服务，不应绕过权威治理规则直接决定知识批准或访问控制。

### 4.6 DerivedKnowledge 与失效传播

派生知识是基于一个或多个既有知识对象推导、归纳或汇总而来的内容。它需要明确记录父对象、推导来源和运行版本。父级证据或知识状态改变时，应能把依赖项标为过期或待重算，而不能继续把陈旧派生结果作为当前权威结论。

用户反馈、Agent Memory 和对话状态与企业知识库的原始证据知识是不同的数据域。Agent Memory 是供特定主体或 Agent 工作流使用的记忆能力；除非经过明确的导入、证据关联和治理流程，否则不能自动升级成全局批准知识。

## 5. 知识生产全生命周期

### 5.1 导入与解析

常见入口包括控制台上传、文本接口、外部 REST 接入以及平台支持的数据源同步。Java 编排权限、知识库配置和事务；Python AI Service 负责解析、归一、切片等算法工作。解析后保留来源、文件修订、ContentUnit 与 Evidence。

关键不变量：原文、修订和证据要能回溯；解析或外部模型失败要有可见状态和重试边界；不可用一个索引写入成功来代替原始数据入库成功。

### 5.2 抽取与持久化

抽取从文档或内容单元产生卡片、断言、实体和关系候选。持久化前要建立知识对象与证据的关联，并在短数据库事务中提交权威对象以及对应 Outbox 事件。

抽取事务提交后，仍可能需要图谱投递登记、冲突检测、实体消歧和完成事件发布。当前系统将这些后处理阶段按 `runId` 持久化，阶段失败可使运行进入 `PARTIAL`，后台 Worker 退避重试，也可通过文档重放接口重做失败阶段，而不需要默认重新调用抽取模型。

`SUCCESS` 应表示必需阶段完成；`PARTIAL` 表示知识对象已落库但处理闭环尚未全部完成；阶段状态和文档摘要按运行 ID 隔离，旧运行不能覆盖新运行的当前状态。

### 5.3 状态治理与生命周期

知识状态表达知识是否可用于正式回答及其生命周期。当前正式检索默认采用 `standard` 策略，仅允许 `APPROVED`、`EFFECTIVE`；可显式配置 `permissive` 以加入 `DRAFT`、`UNCERTAIN`，或使用 `custom` 指定白名单。正式生产应保持显式、可审计的策略，不应依赖 LLM 在提示词中自行忽略未批准内容。抽取默认产出 `APPROVED` 正是为了匹配该策略：若产出停留在 `UNCERTAIN`（`strict` 口径），标准策略下新建知识库的知识将召回不到。

知识状态的常见语义如下，具体枚举迁移和操作权限以当前服务和前端为准：

| 状态 | 业务含义 | 正式问答默认可召回 |
|---|---|---|
| `DRAFT` | 新建或编辑中的草稿 | 否 |
| `UNCERTAIN` | 人工退回待确认、或证据/语义仍有不确定性；宽松模式下正文过短且无信息要素的卡片也落此状态 | 否 |
| `APPROVED` | 已通过治理，可以作为正式知识使用 | 是 |
| `EFFECTIVE` | 已生效的知识版本 | 是 |
| `REJECTED` / `INVALIDATED` | 被拒绝或失效的知识 | 否 |
| `SUPERSEDED` / `EXPIRED` | 被更新版本替代或到期的历史知识 | 否 |

状态白名单只决定知识是否具备候选资格，并不替代知识库 ACL、资源 ACL、证据过滤、时间有效性和答案质量门控。

### 5.4 冲突检测与裁决

冲突检测负责发现同一主题、主体、属性或适用范围下可能相互矛盾的知识。检测结果是待治理的候选，不应自动视作确定冲突。处理应考虑证据、来源可信度、适用主体、时间、地域或版本范围。

系统的治理原则是“规则/评分 → AI 裁决建议 → 必要时人工决策”。LLM 可提供辅助判断，但不拥有最终治理权。裁决应记录操作者或判定来源、状态变更、理由和时间，并由 Outbox 推进相应索引更新。

### 5.5 版本、撤销与派生过期

知识更新不应抹去历史。对旧对象执行 supersede、expire 或 invalidate 等生命周期变更时，要保留版本和审核痕迹，让检索视图最终移除不可用旧版本。派生对象依赖的上游变化后应标记 stale，再按既定规则重算或重新审核。

## 6. 知识检索与问答

### 6.1 查询管线

一次标准问答可抽象为：

1. Java API 校验身份、知识库范围、问题参数和场景策略；
2. Python QueryEngine 进行问题规范化或路由；
3. HybridRetriever 并行查询文本、向量、图谱或本地 fallback；
4. 在各检索通道下推知识状态、ACL 标签、知识库和版本过滤；
5. 按通道权重执行加权 RRF 融合候选；
6. 需要时由 Reranker 重排；
7. Context Assembly 组织有长度预算的证据上下文；
8. 答案门控判断证据是否足够以及是否允许生成；
9. 需要生成时调用 LLM，并返回答案、引用、置信/来源信息；
10. 写入 QueryTrace 和审计，供排障、复现和质量评估。

`search` 主要返回候选，`query` 生成答案，`retrieve` 用于取得检索上下文或相关记录；具体请求与响应字段以对外 API 文档为准。

### 6.2 多路召回

| 通道 | 擅长场景 | 主要实现 |
|---|---|---|
| BM25 / 全文 | 专有名词、精确词汇、编号、短语 | Elasticsearch |
| Vector | 同义表达、语义相近、自然语言改写 | Milvus |
| Graph | 实体关联、关系扩展、受控邻域 | Neo4j |
| Local fallback | 开发或外部引擎不可用时的有限降级 | 本地快照存储 |

不同通道的分数不可直接比较，因此使用 Reciprocal Rank Fusion 等排名融合方式；通道分数和名次会保留为诊断信息。Reranker 是融合后提升相关性的阶段，不能绕过权限或知识状态过滤。

双引擎降级要有可观测性：当某个 provider 出错或关闭时，Trace 应记录实际参与的通道和降级原因，避免悄悄改变结果后仍表现为完整召回。

### 6.3 答案资格与引用

检索命中不等于适合回答。答案门控会结合候选分数、证据覆盖和置信条件决定生成、拒答或返回证据不足。引用应指向被实际选入上下文的证据或知识对象，并保留标题、来源、位置、对象类型、通道和 trace 标识等必要元数据。

生成式回答是基于证据的表达，不自动成为新的批准知识。若需把回答沉淀为知识，必须经由显式反馈、提案、证据绑定及治理链路。

### 6.4 查询 Trace 与评测

每次查询的 QueryTrace 是重建检索过程的事实记录，应能关联 `queryId`、Trace ID、重写问题、路由决定、召回通道及数量、候选、重排、最终上下文、模型、延迟、答案和引用。

质量评估不应只看回答是否流畅，还要关注检索召回率、证据忠实度、引用正确率、拒答准确度、权限隔离和延迟。评测数据集与指标用于回归；单次 Trace 用于解释某个请求为何返回该结果。

## 7. 权限、安全与信任边界

### 7.1 两类调用身份

- 控制台用户使用登录会话和用户/角色体系。
- 外部服务使用 API Key；Key 可绑定主体、权限 scope、知识库和授权期限，并支持撤销、限流和审计。

不要把 API Key 放在 Prompt、业务文档或仓库中。Key 明文只应在签发时交给调用方；后续管理页面不应再次暴露。

### 7.2 授权的多层防线

一次检索通常需要同时满足：

1. 调用身份有效，且所需 scope 已授予；
2. 请求知识库在主体或 Key 的授权范围内；
3. 用户或资源 ACL 允许访问；
4. 知识对象状态在当前检索策略白名单内；
5. 标签过滤与最终证据、图扩展结果保持一致。

`permissionTags` 是召回过滤条件，不等同授权凭证。即便客户端自行提供标签，也不能放宽服务端授权。权限过滤需向 Elasticsearch、Milvus、Neo4j 的查询侧下推，并在需要的图扩展或上下文组装阶段再次确保权限闭合。

### 7.3 ACL 变更与索引传播

ACL 变化既要更新权威授权，也要推进派生索引更新。传播延迟和失败必须可观测；高风险收紧权限时，需要明确索引滞后期间的安全策略。不要只依赖“数据写入时过滤一次”，因为用户、角色、Key 和授权可能随时变化。

### 7.4 审计和敏感数据

审计应区分 HTTP/传输成功、JSON-RPC 成败和实际业务结果。记录调用渠道、主体、知识库、方法、对象、状态、耗时、traceId 等可追踪字段；密钥、原文和敏感记忆应按类别脱敏或避免进入普通日志。

## 8. 索引一致性与运维

### 8.1 Transactional Outbox

知识业务事务同时写权威对象和 `t_index_outbox` 事件。提交后 Worker 以短事务领取任务，离开数据库锁后调用 Python 索引接口，再记录成功、重试或死信。该方式允许至少一次投递，因此目标索引必须幂等，并根据对象的单调 `indexVersion` 拒绝旧事件覆盖新状态。

事件通常按聚合对象和版本排序；死信默认可能阻塞同一聚合的后续版本，运维应明确选择 replay 或在确认安全后 skip，并记录审计。`DEAD` 表示派生视图投递遇到终态失败，不代表 MySQL 权威知识被回滚。

### 8.2 抽取后处理阶段任务

抽取后处理阶段有独立持久化检查点和有界重试。按依赖顺序处理索引登记、冲突检测、实体消歧、完成事件等任务；补偿阶段应具有幂等键并只重做失败步骤。它与索引 Outbox 相关联，但两者表达的业务阶段不同，不能把“索引任务成功”误认为“抽取治理闭环完成”。

### 8.3 Schema Release 蓝绿发布

Schema Release 表示检索索引结构版本；`indexVersion` 表示单个知识对象的索引版本，两者不可混淆。蓝绿流程大致为：从 MySQL 读取权威快照 → 分页重建绿色索引 → 校验页 checksum、数量和高水位 → 标记 READY → 管理员激活别名 → 必要时回滚。

重建期间若 Outbox 高水位变化，说明权威源同时有变更；Release 应重新追平并校验，未验证完成的索引不应切为当前读视图。重建和激活操作应受运维 RBAC 保护并保留审计。

### 8.4 运维角色和常用信号

索引运维角色按仓库文档约定分为 VIEWER（查看）、OPERATOR（重放/跳过等操作）和 ADMIN（重建、激活、回滚）。应监控 Outbox backlog、最老待处理年龄、失败率、死信数、重试延迟、索引落后水位、ACL 传播延迟、查询 P95/P99、各通道错误率及答案拒答率。

## 9. 对外知识服务

### 9.1 REST API

版本化外部 API 位于 `/api/v1/external`，包含查询、搜索、文档/文本接入、对象读取、查询回放及事件流等能力。REST、MCP 和 SSE 共用 API Key、授权和可见性规则；具体 endpoint、scope、请求 schema、错误码和 SDK 示例集中维护于 [`EXTERNAL-API.md`](../api/EXTERNAL-API.md)。

### 9.2 MCP 与 Octop

MCP 服务位于 `/api/mcp`，通过 JSON-RPC 暴露按权限过滤的工具与资源能力。当前实现与 Octop 集成文档描述为无状态 JSON POST，具体协议版本协商、通知响应、工具 scope 和已知兼容边界见 [`OCTOP-INTEGRATION.md`](../api/OCTOP-INTEGRATION.md)。典型工具包括知识搜索、知识问答、列出知识库和读取授权对象。

MCP 的 `tools/list` 只是一层发现过滤；每次 `tools/call` 仍需在服务器端重新验证 Key、scope、知识库授权和 ACL。Agent 连接存在不代表其可访问所有知识。

### 9.3 SSE 与平台事件

平台事件作为追加事件记录，供控制台查看和外部 SSE 客户端订阅。事件可能包括摄入完成、知识对象创建、治理决策、冲突解决、ACL 变化、查询执行和索引重建请求。订阅者只能接收其授权可见范围内的事件；历史记录有保留策略，需要配置清理以控制存储增长。

### 9.4 Agent Memory 的边界

Memory Engine 面向 Agent 工作流提供记忆读写，是独立于企业文档知识治理的一种能力。记忆的主体隔离、生命周期和 API 规范参见 [`AGENT-MEMORY.md`](../api/AGENT-MEMORY.md)。把记忆内容转为可共享企业知识之前，仍需明确来源、证据、适用范围和审批状态。

## 11. 用户界面和平台模块地图

Web 控制台围绕知识库、资料/来源、文档处理、知识对象、冲突治理、图谱、查询工作台、权限与 API Key、索引运维、模型配置、事件总线和质量评估展开。前端通过 API 层访问 Java Backend；业务授权不能只靠隐藏按钮，后端必须执行最终鉴权。

Java 与 Python 的职责边界：

| Java Backend | Python AI Service |
|---|---|
| 用户/Key 身份、scope、ACL 和业务授权 | 文件解析与标准化 |
| 权威业务状态、数据库事务与 Flyway | AI 抽取、Embedding 与语义算法 |
| 治理流程、审核、生命周期和冲突流程 | 多路召回、RRF、重排和上下文组织 |
| Outbox、任务、发布和运维 RBAC | LLM Provider、图算法与索引 Provider |
| 外部 API、MCP、SSE、审计 | 算法诊断和检索执行明细 |

## 12. 容易混淆的术语

| 术语 | 含义 | 不要与之混淆 |
|---|---|---|
| Evidence | 指向原始资料版本的核验依据 | 召回分数、模型解释 |
| ContentUnit | 文档切片和检索粒度 | KnowledgeCard |
| `APPROVED` | 知识治理状态 | 索引已经完成 |
| `SUCCESS` | 某处理运行的阶段结果 | 所有外部索引都绝不滞后 |
| `PARTIAL` | 权威知识可能已提交，但部分后处理尚未完成 | 事务整体回滚 |
| `indexVersion` | 单个对象的索引更新顺序 | Schema Release 版本 |
| `schemaVersion` | 一组检索结构/物理索引的发布版本 | 对象生命周期版本 |
| `permissionTags` | 检索过滤维度 | 身份认证或 ACL 授权 |
| `search` | 返回检索候选的接口语义 | 生成式问答 |
| QueryTrace | 记录一次查询实际链路 | 普通应用日志 |
| API Key scope | 某 Key 可执行的能力范围 | 知识库绑定与对象 ACL |
| Graph Provider | 图查询和索引适配器 | 权威知识审批服务 |

## 13. 典型问题定位

| 现象 | 优先检查 |
|---|---|
| 文件上传成功但搜不到 | 文档解析状态 → ContentUnit/Evidence 数量 → Outbox backlog → ES/Milvus 索引状态 → 状态白名单/ACL |
| 找到片段却未形成知识卡片 | 抽取运行、模型响应 schema、证据绑定、`PARTIAL` 阶段任务和错误记录 |
| 卡片存在但正式问答不召回 | Card/Claim 状态、知识库与资源 ACL、标签下推、索引版本、水位和 provider 健康 |
| 召回正确但答案称证据不足 | QueryTrace 候选和分数、答案资格阈值、上下文预算、引用映射、模型输出 |
| 新文档覆盖后仍搜到旧规则 | DocumentRevision supersede、知识生命周期、旧索引 Outbox 顺序和 `indexVersion` |
| 知识更新后外部索引未变 | `t_index_outbox` 状态、Worker lease/重试/死信、AI 索引端幂等响应 |
| 外部 Agent 工具不可见 | Key scope、知识库授权、`tools/list` 过滤、MCP 初始化及 Octop Agent 绑定 |
| 请求返回 403 | Key 有效性、scope、库绑定、用户 ACL、资源权限及部署总开关 |
| 旧权限仍可检索 | 权威 ACL 记录、传播任务、provider 过滤、重建/激活状态和权限滞后指标 |

排障时使用 `traceId` 或 `queryId` 串起调用审计、Backend 日志、AI 请求上下文和 QueryTrace。高风险索引或权限问题先确认 MySQL 权威状态，再核对派生视图，不要先直接修 ES/Milvus 数据掩盖源状态错误。

## 14. 设计不变量与审查清单

实现或审查新功能时，至少核对以下不变量：

1. 知识结论可追溯到具体来源、文档修订和 Evidence；
2. 模型输出不能单独越权决定知识状态；
3. 正式召回在每个 provider 侧应用服务端状态和 ACL 过滤；
4. 所有外部工具调用都重新检查身份、scope、知识库和资源授权；
5. 业务表与 Outbox 在同一短事务提交，外部索引调用不持有该事务；
6. Worker 可重复投递，索引端依赖幂等键和版本比较；
7. `PARTIAL` 可追踪并能重做失败阶段，不通过重新抽取掩盖补偿缺口；
8. 冲突、审核、版本替代、失效和派生过期都有审计记录；
9. 查询结果可以通过 Trace 解释来源、过滤、排序和模型调用；
10. Schema 发布、重建、激活和回滚有校验、水位和运维授权；
11. 事件、QueryTrace、API Key 和 Agent Memory 的敏感内容遵守保留与脱敏策略；
12. 代码、API schema、数据库迁移、测试、文档和部署配置共同更新。
