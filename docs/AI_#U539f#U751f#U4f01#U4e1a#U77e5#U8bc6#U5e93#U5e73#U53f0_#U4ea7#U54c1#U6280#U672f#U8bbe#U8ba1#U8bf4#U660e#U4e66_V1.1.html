版本：V1.1状态：设计基线面向：产品、架构、研发、AI 工程、知识运营日期：2026-09
文档目标
本设计将知识库定义为“可持续生产、裁决、发布、检索和演进的知识系统”，而非传统的文档向量检索系统。核心对象从文档/内容块（Document / Chunk）升级为证据（Evidence）、断言（Claim）、知识（Knowledge）、知识卡片（Knowledge Card）、实体（Entity）和关系（Relation），并通过知识生命周期和统一查询引擎形成闭环。

1. 产品定位与设计原则

知识生命周期

源数据 → 清洗 → 抽取 → 标准化 → 裁决 → 发布 → 索引 → 查询 → 反馈 → 更新 → 退役

知识对象化

以知识卡片、断言、实体、关系和证据作为一等对象，Chunk 作为证据载体而非最终知识。

检索智能化

查询理解（Query Understanding） → 查询改写（Rewrite） → 检索路由（Router） → 多路召回 → 结果融合（Fusion） → 重排序（Rerank） → 上下文装配（Context Assembly） → 大语言模型（LLM）。
核心设计结论：知识不能脱离证据存在；AI 生成的候选知识不得未经裁决直接进入正式知识库；查询策略必须根据问题类型动态选择，而不是所有问题固定走向量检索增强生成（Vector RAG）。

3. 总体产品架构

总体架构采用“产品应用层—业务平台层—知识智能引擎层—数据与索引层—模型与基础设施层”的分层设计。产品模块与技术服务解耦，知识生产链路与知识查询链路共享统一知识模型、权限体系、版本体系和可观测体系。

3.1 架构分层与职责

① 产品应用层
面向知识管理员、业务专家、普通使用者和平台管理员，提供知识采集、加工、裁决、发布、图谱浏览、智能问答和质量运营能力。页面不直接感知底层向量库或图数据库，通过统一业务接口访问知识能力。
② 业务平台层
由 Java / Spring Boot 承担稳定、强一致的企业业务能力：身份权限、知识库空间、数据源、知识对象元数据、版本、审核工作流、发布状态、审计和统一查询入口。该层是平台的“控制面”。
③ 知识智能引擎层
由 Python AI 服务承担模型密集型与算法密集型能力，包括解析、抽取、实体归一、语义去重/合并、断言校验、知识裁决、图谱构建、检索编排、重排序和上下文装配。该层是平台的“智能计算面”。
④ 数据与索引层
MySQL 保存权威状态和可审计元数据；对象存储保存源文件及解析产物；全文索引解决精确术语检索；向量索引解决语义相似检索；图数据库承载实体关系、多跳路径和冲突/依赖网络。任何索引均属于可重建派生数据，不作为唯一权威数据源。
⑤ 模型与基础设施层
统一管理大语言模型、向量模型、重排序模型、OCR/版面模型以及 Redis、消息队列、任务调度、日志指标等基础设施。通过模型适配层隔离具体模型供应方，便于本地模型与外部模型切换。

3.2 核心技术链路

数据接入→解析与清洗→知识抽取→裁决与发布→多模索引
用户问题→查询理解/改写→检索路由/多路召回→融合与重排序→上下文装配/答案生成

两条链路通过统一的知识标识、版本号、证据链、权限标签和状态字段连接，确保“生成什么、发布什么、检索什么、回答引用什么”能够完整追踪。

5. 知识生成流水线（Pipeline）

5.1 阶段 1（Stage 1）：源数据保存

所有原始输入必须先落库或对象存储，形成不可变的 来源版本（Source Version）。使用文件 Hash、来源 URI、作者、采集时间、版本号建立可追溯链。

Source → SourceVersion → Document → RawContent
                         └→ source_hash / version / authority / timestamp

5.2 阶段 2（Stage 2）：解析与知识清洗

  1. 文件类型识别、OCR、版面解析。
  2. 恢复标题层级、段落、表格、列表及代码块。
  3. 去页眉页脚、重复内容、乱码与无效噪声。
  4. 建立 Hierarchical Semantic Chunk：Chapter → Section → Paragraph → Sentence。
  5. 保留 source offset、page、heading path、parentId，保证证据可定位。

5.3 阶段 3（Stage 3）：大语言模型（LLM）知识抽取

ContentUnit ↓ Knowledge Extraction ├── Entity ├── Concept ├── Claim / Assertion ├── Relation ├── Scenario ├── Condition ├── Procedure └── Knowledge Card Candidate

5.4 阶段 4（Stage 4）：实体归一与知识合并

通过别名词典、规则匹配、向量表示（Embedding）相似度和图谱上下文完成实体归一/消歧（Entity Resolution）；再执行语义去重（Semantic Dedup）与语义合并（Semantic Merge）。语义等价且适用条件一致的候选知识可合并；结论相同但适用版本、时间或条件不同的知识应保留独立版本并建立关联，避免错误覆盖。

5.5 阶段 5（Stage 5）：知识裁决

Candidate ↓ 重复检测（Duplicate Check） ↓ 语义合并（Semantic Merge） ↓ 冲突检测（Conflict Detection） ↓ 证据/权威性/时效性评分（Evidence / Authority / Freshness Scoring） ↓ AI 智能裁决（AI Judge） ├── APPROVED ├── SUPPORTED ├── PARTIALLY_SUPPORTED ├── UNCERTAIN ├── CONFLICTED └── REJECTED ↓ 人工审核（Human Review，按风险与置信度路由） ↓ EFFECTIVE / EXPIRED / SUPERSEDED
裁决原则：低置信度、高风险、强冲突、关键生产配置类知识不得仅依赖 LLM 自动批准；必须进入人工审核或双重证据校验。

5.6 阶段 6（Stage 6）：知识卡片与图谱构建

裁决通过后，生成知识卡片（Knowledge Card）；同时写入实体（Entity）、关系（Relation）、断言（Claim）、证据（Evidence）图结构，并生成对应向量表示（Embedding）和全文索引。

5.7 阶段 7（Stage 7）：知识发布与索引

采用“元数据先发布、索引异步构建”的方式。索引失败不得影响知识版本本身；通过索引状态和重试机制保证最终一致性。

6. 断言（Claim / Assertion）设计

断言（Claim / Assertion）是知识可信性和冲突治理的核心对象。推荐模型：

{
  "claimId": "C001",
  "subject": "Tomcat 8.5",
  "predicate": "SUPPORTS",
  "object": "PKCS12",
  "conditions": ["JDK >= 8"],
  "qualifiers": {},
  "polarity": "POSITIVE",
  "certainty": 0.92,
  "confidence": 0.91,
  "status": "APPROVED",
  "validFrom": null,
  "validTo": null,
  "evidenceIds": ["E001","E002"]
}

逻辑上支持：

IF Condition
THEN Subject -- Predicate --> Object / Value

8. 知识查询流水线（Query Pipeline）

用户问题（User Query） ↓ 查询理解（Query Understanding） ├── 意图（Intent） ├── 实体（Entity） ├── 业务域（Domain） ├── 问题类型（Question Type） └── 对话上下文（Conversation Context） ↓ 查询改写/扩展（Query Rewrite / Expansion） ↓ 检索路由（Retrieval Router） ↓ ┌────────────┬────────────┬────────────┬────────────┬────────────┐ │ 全文/BM25 │ 向量检索 │ 知识卡片 │ 断言检索 │ 图谱检索 │ │ BM25 │ Vector │ Card │ Claim │ Graph │ └────────────┴────────────┴────────────┴────────────┴────────────┘ ↓ 多路召回（Multi-Recall） ↓ 结果融合（Fusion：RRF / Weighted RRF） ↓ 重排序（Rerank） ↓ 上下文扩展（Context Expansion） ↓ 上下文装配（Context Assembly） ↓ 大语言模型（LLM） ↓ 答案 + 引用 + 证据 + 置信度（Answer + Citation + Evidence + Confidence）

8.1 查询路由（Query Router）策略

问题类型主策略增强策略
事实/定义知识卡片（Card）+ 向量检索（Vector）+ BM25断言（Claim）+ 证据（Evidence）
专有名词/错误码BM25 全文检索向量检索（Vector）
关系问题实体（Entity）+ 图谱（Graph）Vector
多跳问题图遍历 / 个性化 PageRank（PPR）知识卡片（Card）+ 证据（Evidence）
全局总结社区摘要 / 全局检索（全局检索（Global Search））Vector
SOP/操作问题知识卡片（Knowledge Card）证据（Evidence）+ 向量检索（Vector）
条件/规则问题断言（Claim）+ 条件（Condition）图谱检索（Graph）
冲突/版本问题断言冲突检索（Claim Conflict Search）来源版本（Source Version）

8.2 多路召回

  • 向量召回（Vector Recall）：内容单元（ContentUnit）、知识（Knowledge）、知识卡片（Card）、实体（Entity）、断言（Claim）。
  • BM25：错误码、接口名、配置项、类名、产品型号等精确术语。
  • 知识卡片召回（Card Recall）：优先召回结构化、已裁决知识。
  • 图谱召回（Graph Recall）：实体链接后执行一跳/两跳（1-hop / 2-hop）或路径查询。
  • 断言召回（Claim Recall）：针对“是否支持、什么条件、是否冲突、为什么”等事实性问题。

8.3 结果融合（Fusion）与重排序（Rerank）

V1 推荐使用倒数排名融合（Reciprocal Rank Fusion，RRF），避免不同召回器原始分值不可直接比较的问题。后续可升级为加权倒数排名融合（Weighted RRF）或基于标注数据的学习排序。

RRF(d) = Σ 1 / (k + rank_i(d))

FinalScore =
  SemanticRelevance
+ KeywordMatch
+ GraphRelevance
+ Authority
+ Freshness
+ Confidence
+ EvidenceScore
+ UserContext

8.4 上下文装配（Context Assembly）

层级内容建议优先级
L1直接回答证据最高
L2已裁决 Knowledge Card高
L3相关 Graph 邻居/路径中高
L4原始 Evidence中
L5历史对话上下文按 Query 决定

上下文装配必须遵守 令牌预算（Token Budget），并避免重复证据、冲突信息无标识混入 提示词（Prompt）。

过期率、版本更新延迟、失效知识命中率

完整性

知识覆盖率、实体关系完整度、场景/条件完整度

可追溯

Source → Evidence → Claim → Knowledge → Answer 全链路

检索质量

召回率（Recall@K）、平均倒数排名（MRR）、归一化折损累计增益（NDCG）、重排序（Rerank）提升率

问答质量

答案正确性（Answer Correctness）、忠实度（Faithfulness）、引用准确率（Citation Accuracy）、无答案率

11.1 知识置信度建议模型

KnowledgeConfidence =
  w1 * ExtractionConfidence
+ w2 * EvidenceSupport
+ w3 * SourceAuthority
+ w4 * Freshness
+ w5 * AdjudicationScore
- w6 * ConflictPenalty

权重不应长期写死，生产阶段应通过标注数据和查询反馈进行校准。

12. 安全、权限与审计

  • 知识库级、分类级、知识级访问控制。
  • 源数据权限必须向下继承到 Evidence、Claim 和 Knowledge Card。
  • 回答只能引用当前用户有权限访问的证据。
  • 所有 AI 生成、人工修改、裁决、发布、撤回操作必须记录 审计日志（Audit Log）。
  • 敏感数据在解析、向量化（Embedding）、提示词（Prompt）、日志中分别实施脱敏策略。
  • 删除/撤销源文档后，必须触发影响分析：哪些 Claim、Card、Graph Edge、Embedding 需要失效。

13. 可观测性与查询追踪（Query Trace）

每一次查询建议产生可重放的查询追踪（Trace）：

queryId
 ├── originalQuery
 ├── rewrittenQueries
 ├── routerDecision
 ├── retrievalStrategies
 ├── recallCandidates

该机制既用于问题排查，也用于后续训练 检索路由器（Retrieval Router）、重排序器（Reranker） 和知识质量模型。

16. V1 建议控制范围

建议 V1 不追求“大而全”。
  • 先支持 PDF、Word、Markdown、HTML 四类数据源。
  • 先实现 实体（Entity）+ 断言（Claim）+ 关系（Relation）+ 知识卡片（Knowledge Card） 四种核心对象。
  • 先实现 向量（Vector）+ BM25 + 知识卡片（Card）+ 图谱（Graph） 四路召回。
  • 先用 RRF + 交叉编码器（Cross-Encoder）/可用重排序模型（Reranker） 完成排序。
  • 先实现 局部图谱（Local Graph） 与有限 2-hop 查询，全局社区检索放到 阶段 4（Phase 4）。
  • 先做 AI 裁决 + 人工审核闭环，不直接做完全自动知识发布。

17. 关键工程风险与应对

风险表现应对

18. 最终架构基线

AI 知识操作系统（AI KNOWLEDGE OS） ┌──────────── 知识生命周期（Knowledge Lifecycle） ────────────┐ │ Source → Clean → Extract → Adjudicate │ │ ↑ ↓ │ │ Update ← Feedback ← Query ← Publish │ └─────────────────────────────────────────────┘ 统一知识模型（Unified Knowledge Model） Evidence → Claim → Knowledge → Card ↓ Entity ↔ Relation ↓ Vector / FullText / Graph 知识查询（Knowledge Query） Query → Understand → Rewrite → Route → Multi Recall → Fusion → Rerank → Context Assembly → LLM → Answer + Citation + Evidence 知识治理（Governance） Permission · Version · Confidence · Conflict Review · Expiration · Audit · Evaluation

19. 结论

本平台的核心不是“建设一个更大的向量数据库”，而是建立一套可解释、可验证、可裁决、可演进的企业知识基础设施。

技术上采用 知识卡片（Knowledge Card）+ 断言（Claim / Assertion）+ 证据（Evidence）+ 知识图谱（Knowledge Graph）+ 混合检索（Hybrid Retrieval） 作为核心模型；以 图谱增强检索生成（GraphRAG）、LightRAG、HippoRAG 等成熟路线作为算法参考；以 查询路由（Query Router）、多路召回（Multi-Recall）、结果融合（Fusion）、重排序（Rerank）、上下文装配（Context Assembly） 构建统一查询引擎。

最终形成从源数据 → 知识生产 → 知识裁决 → 知识发布 → 知识查询 → 反馈 → 知识更新的闭环，使知识库从一次性“数据导入工程”升级为持续运营的 AI 知识操作系统（AI Knowledge OS）。
