# 生成与检索稳定性优化方案

基于 V1.1 闭环验证结果（见 `../development/BACKLOG.md`）：同一份材料三次导入，实体类型从 `VULNERABILITY/PRODUCT` 退化为 `TERM`，派生候选从 1 条掉到 0 条；同一知识库同类问题的答案被证据门控整段拦截（`evidenceGate=BLOCKED`、`claimCount=0`）。

目标三条：**知识生成稳定**、**检索稳定（原文段落块提权 + 忠实度提升）**、**检索规则在页面上讲得清楚**。

---

## 基线（优化前实测）

| 指标 | 现状 |
|---|---|
| 实体类型稳定性 | 同材料 3 次导入，`TERM` 占比 0% → 一部分 → 大部分 |
| 派生链连通率 | kb=7 有 1 条候选；kb=8、kb=9 为 0 条 |
| 答案门控 | kb=9 出现整段 `BLOCKED`，用户只看到兜底句 |
| 忠实度阈值 | `ANSWER_FAITHFULNESS_MIN=0.03`（已是最低档，不是主要卡点） |
| 通道默认权重 | bm25 1.0 / vector 1.0 / card 1.15 / claim 1.10 / graph 1.05 |

---

## A. 知识生成稳定性

### A1 版本与别名归一

`OpenSSL 3.0.12`、`OpenSSL 3.0.13`、`OpenSSL` 各自成实体，且在不同导入中归属不同 → 四跳路径中间断链。

- `app/services/entity_resolver.py`：识别 `<产品> <主.次.补丁>` 模式，归一到产品主实体，版本写入属性/别名。
- 归一结果落库前记录 `mergedFrom`，导入详情可回看"哪些实体被合并、为什么"。

### A2 类型强约束 + 重试

- 抽取 prompt 的实体类型限定为词汇表枚举（`app/core/knowledge_schema.py`），返回后逐条校验。
- 单次抽取结果中 `TERM` 占比 > 60%，或关键类型（`VULNERABILITY`/`PRODUCT`/`CUSTOMER`）全部缺失时，用精简 prompt 重试一次（复用 `extractor` 已有的 strict 通道）。
- 两次都失败才走共现兜底，并在导入任务上标注 `DEGRADED`。

### A3 可观测

导入任务详情增加三项统计：实体类型分布、`TERM` 占比、每条派生预设的链连通率。粒度问题从"只能在数据库里数"变成"导入完就能看见"。

**验收**：同材料连续导入 3 次，类型分布一致（`TERM` 占比波动 < 10%），`OpenSSL` 系列合并为 1 个实体，3 次均产出 ≥ 1 条派生候选。

## B. 检索稳定性：段落块提权 + 忠实度提升

### B1 为什么提权段落块

当前默认权重里，承载**原文段落（chunk）**的两个通道最吃亏：`bm25=1.0`、`vector=1.0`，而结构化对象 `card=1.15`、`claim=1.10`、`graph=1.05`。

后果链：上下文里段落少 → 模型只能引用卡片/图谱摘要 → 引用落在没有 `evidenceCode`/`evidenceHash` 的对象上 → 门控 `exact` 判据不过 → 整句丢弃，句句丢弃就整段 `BLOCKED`。

提权段落块同时解决"检索稳定"和"忠实度"：段落带完整引用元数据，天然能通过门控的精确证据判据。

### B2 通道权重调整（默认）

| 通道 | 现在 | 调整后 | 理由 |
|---|---|---|---|
| bm25（原文段落） | 1.0 | **1.15** | 精确术语/版本号的原文命中，引用最可追溯 |
| vector（原文段落） | 1.0 | **1.15** | 语义命中的原文段落 |
| card | 1.15 | 1.10 | 结构化仍有优势，但不再是压倒性 |
| claim | 1.10 | 1.10 | 不变 |
| graph | 1.05 | 1.05 | 不变 |

### B3 段落块加成 `fusion.chunkBoost`（新增）

在 RRF 融合、质量信号加权之后，对原文段落候选再乘一层加成，让"这一段就是原文"这件事在排序里显式体现：

```
boost = base
      + headingHit × (段落标题是否命中问题词)
      + coverage  × (段落对问题词的覆盖度 0..1)
score *= boost
```

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 总开关 |
| `base` | `1.25` | 原文段落基础加成 |
| `headingHit` | `0.15` | 段落标题（heading_path）命中问题词的额外加成 |
| `coverage` | `0.15` | 覆盖度线性加成上限 |

判定为原文段落：`channel ∈ {bm25, vector}` 且 `object_type` 不属于卡片/断言/图谱。

### B4 上下文保底原文段落 `answer.minChunkEvidence`（新增，默认 3）

装配上下文时先保证至少 N 条原文段落进入提示词，再按分数补其余证据，避免高分卡片把原文挤没。

### B4b 候选层保底（实测必需）

实测发现：kb=9 索引里只有 **3 个 CONTENT_UNIT**（9 个 CLAIM、5 个 CARD），而融合后的 8 条候选全是 GRAPH/CARD —— 段落块压根没进候选，加成自然落在空处。因此补一层候选保底：融合后若原文段落少于 `minChunkEvidence` 条，从各通道召回结果里把排名最高的段落补回候选集（不挤掉任何已入选候选）。

顺序变为：召回 → RRF 融合 → **段落候选保底** → 质量加权 → **段落加成** → 重排 → 上下文装配（段落再保底一次）。

### B5 忠实度判据改进

`answer_evidence_gate._support_score` 现在是"命中词元数 / 句子词元数"，对长句和版本串不友好。改为加权覆盖：版本号、错误码、英文专名等"可验证词元"权重 2.0，其余词元 1.0，语义不变（仍是与证据的重合度），但关键实体一命中就能得分。

> 阈值不动：0.03 已经在最低档，继续下调只会放行噪声。真正的卡点是 `exact`（引用必须带 `evidenceCode` + `evidenceHash`）与逐句强校验，B1–B4 正是从源头增加"带完整引用的原文证据"供给。

### B6 拦截构成可观测

门控结果新增三类拦截计数，页面能直接看出该动哪里：

```
blockReasons: { missingCitation: n, nonExactEvidence: n, lowFaithfulness: n }
```

**验收**：kb=9 同类问题不再整段 `BLOCKED`（至少 `PARTIAL` 且保留结论与图谱路径一致）；段落块在上下文中的占比 ≥ `minChunkEvidence`；门控结果给出三类拦截计数。

## C. 检索规则在页面上讲得清楚

现有 `QueryPolicyPanel` 已经能配置六段（路由 / 改写 / 召回 / 融合 / 重排 / 答案），缺的是"这套配置到底怎么作用"的一句话解释和证据级的加成分解。

### C1 策略面板新增「段落块与忠实度」区块

暴露 B3 的四个字段与 B4 的 `minChunkEvidence`，每项带一句作用说明（写清楚加在哪个阶段、影响什么）。

### C2 生效规则速览（面板顶部）

按当前策略实时生成一句人话，例如：

> 命中 `RELATION` 规则 → 通道 图谱/向量/知识卡（权重 1.05 / 1.15 / 1.10）；RRF k=60；原文段落加成 ×1.25（标题命中 +0.15，覆盖度 +0.15）；重排开启；上下文 8000 字含原文段落保底 3 条；忠实度阈值 0.03、断言覆盖 0.08。

### C3 证据级加成分解

`ScoreBreakdownPanel` 在"为什么命中"里补上段落块加成一项（如"原文段落加成 ×1.40（标题命中、覆盖度 0.62）"），与已有的通道命中、质量加成、重排分并列。

**验收**：一个不熟悉系统的人打开策略页，30 秒内能说出"这次检索用了哪些通道、原文段落有没有加成、答不上来会被什么阈值拦住"。

## 实测结果（kb=9，方案 1–3 步落地后）

同一知识库、同一问题「CVE-2026-1234 会影响哪些客户？请给出影响路径。」

| | 优化前 | 优化后 |
|---|---|---|
| 证据门控 | `evidenceGate=BLOCKED` | **`evidenceGate=PASS`** |
| 交付状态 | 整段替换为"现有知识不足以…" | `PARTIAL`，保留 11/12 条结论 |
| 答案内容 | 无 | 给出完整影响路径：`SecureGateway V5.2 → 上海银行安全网关项目 → 上海银行` |
| 候选构成 | 8 条全为 GRAPH/CARD | 11 条，含 3 条 CONTENT_UNIT（`chunkBoost` 1.44 / 1.29 / 1.27） |

关键发现：提权的前提是段落块先进入候选。kb=9 索引里只有 3 个 CONTENT_UNIT（9 个 CLAIM、5 个 CARD），融合后段落全被挤掉 —— 所以补了 B4b 候选层保底，加成才真正落到段落上。

剩余拦截来自结构化门控（冲突/证据不足），属下一步优化点。

## 实施顺序

1. B2/B3/B4 —— 策略字段与默认权重（配置层，风险低）
2. B5/B6 —— 门控判据与拦截构成（有测试覆盖）
3. C1/C2/C3 —— 前端配置与可解释展示
4. A1/A2/A3 —— 实体归一与类型强约束（改动面最大，单独一轮）

每步都跑 `ai-service` 的 pytest 与后端相关测试，第 1–3 步完成后用 kb=9 复验门控结果。
