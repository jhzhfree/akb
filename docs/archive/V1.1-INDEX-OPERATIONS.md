## V1.1 索引运营、蓝绿升级与故障演练说明

### 1. 本轮目标

在 Transactional Outbox + Index Worker 基础上补齐四类生产能力：

1. Micrometer/Prometheus 可观测性；
2. Outbox/Delivery Attempt 生命周期归档；
3. Elasticsearch/Milvus Schema Version 蓝绿重建、校验、激活与回滚；
4. 故障注入与恢复验证入口。

MySQL 继续是权威状态。Elasticsearch、Milvus、Neo4j 仍是可重建 Retrieval View。

### 2. Prometheus 指标

Backend 新增 `micrometer-registry-prometheus`，`/actuator/prometheus` 对内提供指标。

核心指标：

- `llmkb_index_outbox_delivery_total{result="succeeded|retry|dead"}`
- `llmkb_index_outbox_delivery_duration_seconds`
- `llmkb_index_outbox_pending`
- `llmkb_index_outbox_retry`
- `llmkb_index_outbox_dead`
- `llmkb_index_outbox_oldest_lag_seconds`
- `llmkb_index_outbox_stale_recovered_total`
- `llmkb_index_outbox_archived_total`

`monitoring/prometheus.yml` 同时抓取 API Backend 和独立 Index Worker；`monitoring/alerts.yml` 提供 Dead Letter、Lag、Retry backlog 告警规则。

生产 Index Worker 不再以 `web-application-type=none` 运行，而是在内部 8081 提供 Actuator，使 Worker 自身指标可被 Prometheus 抓取。该端口未映射到宿主公网。

### 3. Outbox 归档

Flyway V5 新增：

- `t_index_outbox_archive`
- `t_index_delivery_attempt_archive`
- `t_index_schema_release`

默认保留在线完成事件 14 天。归档任务只处理 `SUCCEEDED/SKIPPED`，不会移动 `PENDING/PROCESSING/RETRY/DEAD`。

归档步骤位于同一个短事务：

```
copy completed outbox -> archive
copy delivery attempts -> attempt archive
delete archived attempts
delete archived live outbox
```

配置：

```
INDEX_OUTBOX_ARCHIVE_ENABLED=true
INDEX_OUTBOX_RETENTION_DAYS=14
INDEX_OUTBOX_ARCHIVE_BATCH_SIZE=500
INDEX_OUTBOX_ARCHIVE_INTERVAL_MS=3600000
```

### 4. 两层版本语义

对象版本与 Schema 版本严格分开：

- `indexVersion`: 单个 Aggregate 的单调业务索引版本，用于防止旧事件覆盖新事件；
- `schemaVersion`: Elasticsearch Mapping / Milvus Collection 结构版本，用于蓝绿发布。

不能使用时间戳替代任一版本。

### 5. 蓝绿索引流程

```
ACTIVE v1 alias
      |
      +---- query traffic

create v2 physical targets
  Elasticsearch: <base>__v2
  Milvus:     <base>__v2
      |
      v
full rebuild
      |
      v
count validation against MySQL authoritative count
      |
      +-- mismatch -> VALIDATION_FAILED, refuse activation
      |
      v
READY
      |
      v
atomic read-alias switch
      |
      v
ACTIVE v2 / RETIRED v1
```

默认读别名：

```
ELASTICSEARCH_READ_ALIAS=llmkb_knowledge_read
MILVUS_READ_ALIAS=llmkb_knowledge_read
```

旧物理索引不在激活时删除，可用同一个 activate API 把 alias 切回 RETIRED release，完成快速 rollback。

#### API

```
POST /api/knowledge/index/schema/{kb}/rebuild?schemaVersion=v2
GET  /api/knowledge/index/schema/{kb}
POST /api/knowledge/index/schema/{kb}/activate/{releaseId}
POST /api/knowledge/index/schema/{kb}/rollback/{releaseId}
```

Schema Release 状态：

```
BUILDING -> READY -> ACTIVE -> RETIRED
        \-> VALIDATION_FAILED
        \-> FAILED
```

只有 READY / ACTIVE / RETIRED release 可被激活。

### 6. 当前重建源与安全约束

本轮 AI Service 的蓝绿物理目标构建仍以本地 Retrieval Store 为数据流入口，但 Backend 使用 MySQL `countIndexableObjects` 作为权威数量进行发布前校验；数量不一致将标记 `VALIDATION_FAILED` 并阻止 alias 切换。

这比直接覆盖线上索引安全，但仍不是最终形态。下一版建议把全量重建改成：

```
MySQL authoritative snapshot/page stream
 -> Rebuild Worker
 -> Elasticsearch/Milvus green targets
```

同时加入内容 checksum / aggregate high-watermark，而不是只做 count validation。

### 7. 故障演练

新增：

```
scripts/fault-injection-indexing.sh
```

典型流程：

1. 停止 Milvus；
2. 对现有 Card/Claim 发起状态变化，产生 Outbox；
3. 验证业务事务成功、Outbox 进入 RETRY；
4. 恢复 Milvus；
5. 验证 Worker 自动补偿到 SUCCEEDED；
6. 检查 Prometheus retry/dead/lag 指标。

进一步必须在部署环境验证：

- 连续故障直到 DEAD；
- DEAD 阻塞同 aggregate 新版本；
- replay 后版本顺序恢复；
- skip 后明确释放后续版本；
- Worker kill -9 后 stale lock recovery；
- Elasticsearch/Milvus alias 切换时并发查询不中断；
- v2 激活后 rollback 到 v1；
- 归档任务运行期间 Worker 并发消费无误删。

### 8. 自动 Gate

统一 Gate 从 18 项扩展到 20 项，新增：

- Blue/green schema mock contract；
- Index operations / observability contract；
- V5 Flyway 结构检查；
- Prometheus/alert YAML 和 compose 解析。

本环境执行结果：20/20 static/smoke gates passed。

当前环境没有 Maven/Docker，因此以下内容仅配置了测试/CI，未在本机真实运行：

- Testcontainers MySQL 8 V5 migration；
- 多 Worker `FOR UPDATE SKIP LOCKED`；
- Prometheus 实际 scrape；
- Elasticsearch/Milvus 真容器 alias 切换；
- stop/start 故障注入。

### 9. 下一阶段建议

V1.1 此时已经具备生产索引体系的关键骨架。下一轮建议重点从“索引基础设施”转向：

1. MySQL authoritative snapshot 全量重建 Worker；
2. checksum/high-watermark 一致性校验；
3. SLO Dashboard（检索 P95、Outbox lag、索引 drift、AI latency）；
4. RBAC/运维 API 权限与审计；
5. Outbox 分区/归档表冷热存储；
6. 多知识库/多租户索引隔离策略。

## V1.1 MySQL Authoritative Snapshot Rebuild + Integrity + SLO + Ops RBAC

### 1. 本轮目标

本轮在 Transactional Outbox、Elasticsearch + Milvus 双检索、蓝绿索引发布的基础上，补齐四个生产能力：

1. MySQL authoritative snapshot rebuild：蓝绿重建直接从权威业务表分页读取，不再依赖 JSON fallback。
2. Checksum + High-Watermark：发布前不仅校验数量，还记录快照摘要和 Outbox 水位，避免重建期间源数据变化后误切旧索引。
3. SLO Dashboard：Prometheus + Grafana 提供接口 P95、5xx、Outbox Lag/Retry/Dead、投递 P95、JVM Heap 等核心运行指标。
4. Ops RBAC：对索引运维 API 增加 VIEWER / OPERATOR / ADMIN 三级授权。

### 2. 权威重建链路

```text
MySQL authoritative tables
  ├─ t_content_unit + document/source
  ├─ t_knowledge_card
  └─ t_claim
          ↓ page=500
Canonical Snapshot Page
          ↓ page checksum
 t_index_schema_snapshot_audit
          ↓
AI /rebuild-batch
          ↓ embedding
  ┌───────┴────────┐
Elasticsearch Green  Milvus Green
          ↓
count + source high-watermark validation
          ↓
READY / VALIDATION_FAILED
          ↓
alias switch
```

每个 Release 在开始时记录 `source_high_watermark = MAX(t_index_outbox.id)`，结束后再次读取 `source_end_watermark`。如果两者不同，说明重建期间源知识发生了写入，Release 被标记为 `SOURCE_CHANGED / VALIDATION_FAILED`，不能激活。

这是保守一致性策略：宁可重新构建，也不把已知过期的 Green Index 切上线。

### 3. 快照完整性

新增 Flyway：

`V6__authoritative_snapshot_and_release_integrity.sql`

`t_index_schema_release` 新增：

- snapshot_checksum
- source_high_watermark
- source_end_watermark
- snapshot_count
- integrity_state

新增：

`t_index_schema_snapshot_audit`

每页记录：

- release_id
- page_no
- row_count
- page_checksum
- first_object_key
- last_object_key

最终 `snapshot_checksum` 是按顺序聚合各页 checksum 得到的 SHA-256，可用于发布审计和后续重建对比。

### 4. 一致性判定

Release 进入 READY 需要同时满足：

```text
snapshot_count == authoritative expected_count
Elasticsearch indexed_count == expected_count
Milvus indexed_count == expected_count
source_high_watermark == source_end_watermark
```

否则进入：

- COUNT_MISMATCH
- SOURCE_CHANGED
- VALIDATION_FAILED

不会执行 alias switch。

### 5. 运维 RBAC

保护范围：

`/api/knowledge/index/**`

认证头：

`X-Ops-Token`

权限分级：

| Role | 能力 |
|---|---|
| VIEWER | GET Outbox、Drift、Schema Release、统计 |
| OPERATOR | VIEWER + replay / skip |
| ADMIN | OPERATOR + rebuild / activate / rollback 等写操作 |

配置：

```text
OPS_RBAC_ENABLED=true
OPS_VIEWER_TOKEN=<random token >= 24 chars>
OPS_OPERATOR_TOKEN=<different random token>
OPS_ADMIN_TOKEN=<different random token>
```

生产启动诊断会拒绝：

- 空 token
- 少于 24 字符
- 包含 change-me 的默认 token
- 三个 role token 相同

开发环境默认 `OPS_RBAC_ENABLED=false`，便于本地调试。

### 6. SLO Dashboard

新增 Grafana provisioning：

- `monitoring/grafana/provisioning/datasources/prometheus.yml`
- `monitoring/grafana/provisioning/dashboards/llmkb.yml`
- `monitoring/grafana/dashboards/llmkb-slo.json`

核心面板：

- Backend API P95 latency
- Backend 5xx rate
- Outbox oldest lag
- Retry backlog
- Dead letter count
- Index delivery P95
- JVM heap usage

新增告警：

- Backend P95 > 1.5s 持续 10 分钟
- Backend 5xx > 1% 持续 5 分钟
- Outbox lag > 120s
- Retry backlog > 20
- Dead letter > 0

### 7. 当前蓝绿发布状态机

```text
BUILDING
   ↓ authoritative snapshot
   ↓ batch rebuild
   ↓ checksum / count / watermark validation
READY
   ↓ ADMIN activate
ACTIVE
   ↓ next release activation
RETIRED
   ↘ rollback → ACTIVE

Validation failure:
BUILDING → VALIDATION_FAILED
```
