1. 设计基线与总体原则

知识生成主页面交互约束：左侧不再出现“文档导入、连接器、生成配置、知识台账、知识裁决、知识衍生”等二级菜单。主页面顶部使用四个任务入口卡片：导入文档 / 连接数据源 / 知识裁决 / 知识衍生；下方使用 生成概览 / 生成配置 / 文档导入 / 连接器 / 外部知识 / 知识台账 / 知识裁决 / 知识衍生 Tab 组织完整工作区。

详细设计承接 PRD V2.1，将产品从“功能模块集合”重构为围绕知识资产的五个用户任务域：看知识、建知识、找知识、接知识、管平台。

知识概览看知识
知识生成建知识
知识检索找知识
接口服务接知识
系统配置管平台
术语调整：“接口服务”（原“知识集成”）比“知识应用”更准确。该一级菜单的核心不是在平台内创建各种终端应用，而是把可信知识能力通过 API、MCP、SSE、凭证等方式接入现有业务系统、AI 应用、Agent 与工作流。

2.3 角色菜单与可见性

角色决定“能不能做”，角色菜单配置决定“看得见多少”。实现上没有可手动切换的视图：前端外壳用 visibleLeaves(section, can, role, menu) 计算当前可见 Tab，优先级为 后端下发的角色菜单（t_role_menu）> 管理员专属标记（adminOnly）> 权限码（permission）。后端 menu 非空时它就是权威来源；为空才回落到内置规则，保证老会话与未登录场景不白屏。页面自身不重复判定角色。

落点规则：进入模块时落在第一个可见 Tab（知识生成即「文档导入」、接口服务即「服务」），不需要额外配置默认页；旧书签落到不可见页面时自动回落到该模块默认页。未知角色一律降级为 VIEWER（最小权限集）。

2.4 底部页脚（版本与授权）

主内容区最下方固定一条页脚，所有页面共用：左侧为产品名 + 产品版本徽标 + 运行环境/服务版本（取自 /api/knowledge/env，未取到时省略），右侧为授权说明「企业自部署 · 版本与授权由部署镜像管理」与「版本信息」入口（打开版本信息弹窗：服务版本、运行环境、核对时间、检查更新）。侧栏底部不再单独显示版本号。

2.2 主题与视觉规范（深浅双主题）

呈现层不再按页面各自调色，所有组件只消费一套主题 token：同一个语义在深色与浅色下取不同值，组件只写“主文本 / 次级表面 / 成功态”这类语义，不写具体色值。新增一个主题只需新增一组变量，不改任何组件。

2.2.1 主题切换与作用域

项规则
切换入口顶栏右侧；切换后整站（含顶栏、侧栏、弹窗、抽屉、表格、图谱画布、登录页）同步变化。
三档循环点击在 浅色 → 深色 → 跟随系统 三档间循环（图标 ☀ / ☾ / ◐），与实现一致；跟随系统档实时响应 prefers-color-scheme。
持久化本地存储保存选择（dark / light / system），刷新与重新登录保持；未选择时默认浅色。
作用域主题作用于根节点的 data-theme，所有变量在该作用域下重定义；组件无需感知当前主题。
对比度正文与背景对比度不低于 4.5:1；弱化文字不低于 3:1；状态色在两种主题下都必须落在“可读”区间。

2.2.3 按钮三档

档位形态用于两主题表现
主操作品牌色实心 + 白字 + 品牌色边框页面唯一主行动点：生成知识、开始导入、发布服务形态一致，仅品牌色深浅不同
次操作表面底 + 可见边框 + 主文本刷新、重试、预览、批量操作边框在深色下必须可见，否则会退化成一块看不出边界的深色
弱操作无边框 + 次级文字，hover 才出现底色取消、关闭、次要链接同上
危险操作危险色实心 + 白字删除、停用、废止同上
切换类按钮（如“文档 / 文本分块 / 实体归一”）统一写成「次操作 + 选中即切主操作」，并依赖样式层顺序保证主操作覆盖次操作；禁止用透明度、下划线或自绘底色表示选中。

2.2.5 第三方组件的主题桥接

表格、标签、按钮、进度条、弹窗、分页等基础组件来自 Element Plus，其默认皮肤是浅色的。做法是把组件的 CSS 变量整体接到本套 token 上（背景、文字、边框、填充、状态色及其浅色变体），使它们在深色主题下自动变成深色底 + 亮色字，在浅色主题下使用本套状态色，而不需要逐个组件写主题分支。

收益：状态色在“自己写的胶囊”和“第三方组件的标签”上完全一致；新增主题时第三方组件自动跟随。

2.2.6 实施纪律

禁止替代做法
在组件里写固定调色板色（如“浅绿底 + 深绿字”）使用状态胶囊类，配色由主题给出
用品牌色原色当文字色使用强调文字色（深色下更亮、浅色下更深）
用灰色写死边框、分割线使用分割线 / 边框变量
用透明度表示禁用或弱化使用弱化文字色与禁用态样式
每个页面自定义按钮与标签使用按钮三档与状态胶囊

4. 知识生成详细设计

路由：/knowledge/generate。页面顶部 Tab：生成概览 / 生成配置 / 文档导入 / 连接器 / 外部知识 / 知识台账 / 知识裁决 / 知识衍生。

菜单裁剪：生成概览 / 连接器 / 外部知识 / 知识台账标记管理员专属；生成配置不按角色裁剪，只要求 generate:import（与「文档导入」同级）。文档导入 / 知识裁决 / 知识衍生对持有 generate:import / generate:judge / generate:derive 的角色开放；过滤后第一个可见 Tab 即该角色的默认落点（管理员之外通常就是「文档导入」）。

4.2 连接器

Profile 采用“基础设置 + 高级设置”。基础设置仅包含知识范围、搜索模式、TopK；高级设置包含权重、阈值、RRF K、Reranker、Graph Expansion、Context Window。

5.5 检索链路追踪（Query Trace）

以 traceId 为单位查看一次问答的完整链路：查询理解、多路召回、融合排序、重排、上下文装配与生成，以及各阶段耗时、模型与索引版本。列表按时间倒序分页（10 / 20 / 50 / 100 条每页，带总数与页码），避免长列表一次拉全量；排序在时间戳之外补 id DESC，否则同一秒的多条记录翻页会重复或漏行。每行展示调用方 IP（按 X-Forwarded-For、X-Real-IP 解析，取不到记为空不影响其它列），便于把异常调用定位到具体来源。从智能检索结果卡片与问答历史的「查看完整链路」可直达对应链路。

5.6 回答反馈

收集真实问答中暴露的问题与修正建议（答错、引用不准、缺失知识等）。反馈不直接改写知识：经人工确认后才进入知识治理流程，避免未核实的反馈被写进知识库。每条反馈关联到当时的 trace，可回溯检索与生成过程。

6.5 MCP

MCP 页面分为 Server 配置、Tools/Resources 列表、权限范围、测试控制台和调用日志。工具名以 McpServerService 为准，文档与客户端都不得自行改名：knowledge_query、knowledge_search、list_knowledge_bases、list_knowledge_cards、get_knowledge_card、list_claims、get_claim、get_evidence、graph_neighbors；另有按 Scope 动态下发的 ingest_text（需 INGEST）与 Memory 三件套 memory_recall / memory_capture / memory_forget（需 MEMORY_MANAGE）。V2.1 初稿曾写作 search_knowledge、retrieve_context、get_assertion、explore_entity ——这些名字在代码中不存在，已废弃。MCP 不建立第二套权限模型，复用集成服务 Credential + Knowledge ACL。

6.6 SSE

事件名以 ExternalStreamService 为准。除 open / done 外，进度统一走 stage 事件，stage 取值与 AI 服务上报的阶段一致，前端据此渲染真实进度而不是自造一个。

event: open data: {"traceId":"..."} event: stage data: {"stage":"recall","label":"多通道召回","results":5} event: knowledge data: {"objectType":"CARD","code":"..."} event: citation data: {"evidenceCode":"ev_1","documentCode":"doc_1","page":38} event: delta data: {"text":"..."} event: done data: {"usage":{},"latencyMs":1280} event: error data: {"code":"...","message":"..."}

stage 的全部取值（顺序固定，与 PIPELINE_STAGES 一致）：rewrite 查询改写、route 意图路由、recall 多通道召回、acl_filter 权限过滤、fusion 结果融合、rerank 重排序、context 上下文装配、llm 答案生成、citation 引用校验。另有 ingestion 事件用于文档摄入进度。

已废弃的事件名：start（→ open）、retrieval（→ stage 且 stage=recall）、complete（→ done）。

6.7 凭证

凭证字段：credentialId、name、type(API_KEY/OAUTH/JWT)、serviceIds、scopes、ipAllowlist、rateLimit、expireAt、status。Secret 仅创建时显示一次；列表只显示尾号。

6.8 调用日志

字段：time、service、protocol、client、requestId、traceId、status、latency、retrievalCount、tokenUsage、errorCode、callerIp（调用方 IP），以及传入参数（requestParams）与返回数据（responseData）。点击 traceId 跳转 Query Trace，形成“外部调用 → 检索 → Evidence → Answer”的完整追溯。调用方 IP 按 X-Forwarded-For → X-Real-IP → 直连地址的顺序解析，取不到记为空，不影响其它列。

明文入参与返回（对齐当前实现）：调用日志在列表与详情中直接展示传入参数与返回数据的明文内容（REST 的请求体与响应体、MCP 的工具入参与结果、SSE 的增量与完成事件），便于调用方自查；展示前按系统配置的脱敏规则处理敏感字段。REST / MCP / SSE 三种协议的调用统一落库，协议的入参与返回由请求体缓存与响应包装统一采集，避免不同协议各写一套。

6.9 外部主体与多知识库授权

凭证背后是调用主体（Principal），授权挂在主体而不是单个 Key 上：一个主体可持有多个 API Key，也可被授予多个知识库。本节讲数据模型与配置约束，运行时的授权判定与标签收窄见 10.1.5。

项设计

10. 权限与状态设计

ACL 抽象：USER/ROLE/DEPARTMENT/GROUP → SPACE/SOURCE/DOCUMENT/CARD/ENTITY/ASSERTION → READ/WRITE/REVIEW/MANAGE。落地实现见 10.1——动作维度收敛为读与写，来源继承未实现（对象各自持有标签，原因见 10.1.7），其余差异也在 10.1.7 一并说明。

10.1 权限模型：四层落地与判定顺序

本节承接章首的 ACL 抽象，写当前代码的实际落地。抽象里的“USER/ROLE/DEPARTMENT/GROUP → SPACE/SOURCE/… → READ/WRITE/REVIEW/MANAGE”在实现中收敛为四层闸门，动作维度只保留读与写两种；与抽象的差异集中在 10.1.7 说明。

层拦截 / 判定点关键类与表开关
① 会话AuthInterceptor（order 1，全 /api/**）t_auth_session、t_user、AuthContextknowledge.auth.enabled / allow-anonymous
② 功能权限PermissionInterceptor（order 3）Permissions、t_role_menu、RoleMenuService—
③ 库可见性KnowledgeBaseAccessInterceptor（order 2，只挂 /api/knowledge/**）t_knowledge_base、t_user_group_member—
④ 对象标签控制器显式调用 AclContextResolverpermission_tags 列、t_acl_*、t_entity_acl_scope / t_relation_acl_scopeknowledge.acl.identity-db-enabled / trusted-header-enabled / external-tag-mode

10.1.1 判定顺序。三个拦截器按 order 串联，顺序不能换：先确认身份（①），再判断功能（②），最后判断具体库（③）。之所以让库访问在功能权限之后，是为了把“这个角色根本不该用这个功能”和“这个角色能用功能但不能进这个库”区分成两种错误——前者 403 且不需要知道库是否存在，后者只在已通过功能校验后才暴露库维度的结论，避免用错误码探测库的存在性。④ 不在拦截器里，因为对象标签需要按请求体里的检索范围动态计算，由各控制器在组装请求时统一调用 aclContextResolver.resolve(header) 注入。

10.1.2 功能权限的派生。权限码是字符串常量（system:acl、generate:import、search:graph……），由 Permissions 维护，require() 抛 SecurityException 由全局异常处理映射为 403。角色到权限码不是静态表，而是该角色可见菜单项的并集：

permissionsFor(role): if role == ADMIN: return Permissions.all() out = {} for key in visibleKeys(role): # 来自 t_role_menu(role_code, leaf_key, visible) p = MenuCatalog.permissionOf(key) # 菜单项 → 权限码 if p != null: out.add(p) return out

UserRole 里列举的默认集只用于初始化 t_role_menu；未知角色一律降级为 VIEWER（最小集），避免脏角色数据变成越权。Permissions.has() 在 AuthContext 为空时返回 true，与“未开启认证即全放行”保持同一套语义，这一点前后端必须一致（前端 hasPermission(null, code) 同样全放行）。接口侧由 PermissionInterceptor 的“路径 → 权限码”规则表匹配，规则从具体到宽泛、命中第一条，写操作可只拦非 GET（WRITE_ONLY）。没有 t_role_permission：菜单即权限面。

10.1.3 库可见性与读写判定。库只有三态可见性（PUBLIC / PRIVATE / GROUP，null 或未知值按 PUBLIC），读判定：

canRead(user, base): if user.role == ADMIN: return true switch base.visibility: PUBLIC: return true PRIVATE: return base.created_by == user.id GROUP: return base.created_by == user.id or countGroupMember(base.owner_group_id, user.id) > 0 canWrite(user, base): if user.role in (ADMIN, KNOWLEDGE_ADMIN): return true return base.created_by == user.id or (user.role.canWriteKnowledge() and canRead(user, base))

canWriteKnowledge() 覆盖 ADMIN / KNOWLEDGE_ADMIN / KNOWLEDGE_OPERATOR / KNOWLEDGE_AUDITOR 四个角色。user == null（外部无会话或匿名）时只有 PUBLIC 可读。列表查询在 SQL 层过滤（KnowledgeBaseMapper），管理员的 all=true 才跳过条件。组关系是知识库上的单值 owner_group_id 加成员表 t_user_group_member(group_id, user_id)，没有“组-库”多对多表——一个库只归属一个组，需要多组共享时用 PUBLIC 或标签控制。

10.1.4 对象标签与三态语义。标签落在业务对象上（t_source / t_knowledge_card / t_claim 的 permission_tags JSON 列），主体标签由六张 ACL 表解析：

resolveAclPermissionTags(subjectCode) = subject 直挂 (t_acl_subject_tag) ∪ 角色挂 (t_acl_subject_role → t_acl_role_tag) ∪ 部门挂 (t_acl_department_tag)

AclContextResolver.resolve() 的返回值是整套 ACL 的语义核心，三态必须严格区分：null = 不受限（ADMIN、KNOWLEDGE_ADMIN、未开认证），查询不加任何条件；[] = 只能看公开内容；非空数组 = 公开内容加命中任一标签。若把 [] 与 null 混为一谈，不是越权就是全员失明，这是实现中最容易被改坏的一处。三种存储的过滤写法不同、语义相同：MySQL 用 JSON_LENGTH(permission_tags)=0 或 JSON_CONTAINS；Elasticsearch 用 bool.should（must_not exists 或 terms，minimum_should_match=1）；Milvus 用 json_contains_any 并固定带上 __public__。图谱侧为避免跨来源实体聚合后越权，单独落 t_entity_acl_scope / t_relation_acl_scope（按 source_id 记录该实体/关系的可见范围）。标签变更写 t_acl_change，同时投 outbox 事件 INDEX_OBJECT_ACL 触发索引侧重建，避免权威库与检索索引口径不一致。

10.1.5 外部主体与授权判定。凭证与授权分离：t_api_key（secret_hash、key_prefix、credential_type（SERVICE_KEY / PAT）、owner_user_id、scopes、rate_limit、expires_at、deleted_at，外加 principal_id 与 permission_tags）是凭证，t_principal 是主体，t_principal_kb_grant(principal_id, knowledge_base_id, status, expires_at, permission_tags) 是授权。判定流程：

resolveKnowledgeBase(key, kb, delegated): grants = grantedKnowledgeBases(key) # 委托身份时取 agentGrants ∩ employeeGrants if kb in grants: return kb if key.boundKb != null: if kb != boundKb or key.principalId != null: throw SecurityException if key.principalId != null and grants 非空 and kb not in grants: throw SecurityException accessService.assertExternalAccess(kb, readOnly) # 回落到库可见性（PUBLIC 兜底）

标签收窄：effectiveTags = keyTags ∩ kbGrantTags ∩ delegatedTags，再与请求标签取交；knowledge.acl.external-tag-mode 决定强度——CLIENT 原样使用调用方标签，SHADOW 只记录“本应收窄到 X”的差异告警，ENFORCE 强制收窄且未配置任何授权时默认拒绝。授权写操作有三条硬约束：单主体授权库不超过 100、expires_at 必须晚于当前时间、标签不超过 100 个且单个不超过 128 字符；替换授权时先写 REVOKE 审计再删旧插新，保证审计链不缺环。

10.1.6 前端契约。前端不做权限裁决，只做呈现裁剪。登录只返回 token（t_auth_session），权限与菜单由 GET /api/auth/me 单独下发（permissions、menu、role、homeView），只放内存不落 localStorage。外壳通过 shell 契约暴露四个判定：can(code) 判功能权限码、menuHas(key) 判角色菜单可见性、canNavigate(key) 判页面可达、tabs(section) 取模块内可见 Tab。菜单裁剪优先级是角色菜单配置 > adminOnly > 权限码：后端下发的 menu 非空时它就是权威来源，为空才回落到内置规则。无权限时入口置灰并给出 title 提示，点击兜底提示“当前角色无权访问”，不发请求；401 由 axios 拦截器统一清 token 并派发 kos-auth-expired 事件，App 监听后回登录页，各调用点不各自处理。

10.1.7 与章首抽象的三处差异。① 没有四动作矩阵：实现只区分读写，REVIEW / MANAGE 由功能权限码（如 generate:judge、system:acl）表达，而不是对象级动作。② 没有“Source 权限向下继承”：对象各自持有标签，原因是同一 Source 常喂多个库，继承会造成隐性提权；需要一致时由抽取侧按来源标签写对象标签。③ 没有单一 ACL 总开关：拆为 identity-db-enabled（标签从身份库解析）、trusted-header-enabled（接受可信头传入标签，仅供内网网关）、external-tag-mode（外部标签强度）三个，可独立灰度与回滚。

10.1.8 验证方式。权限有 16 个端到端校验脚本按阶段覆盖，全部是“真打接口 + 断言可见性”的黑盒校验，而不是读代码推断：scripts/check-acl-phase2.py（基础主体与角色）、phase3-governance、phase4-engineering-closure、phase5-orchestrator、phase6-machine-qualification、phase7-manifest-generation、phase8-neo4j-generation、phase9-graph-generation、phase10、phase11-cross-source（跨来源越权）、phase12-facets（分面计数不泄露）、phase13-evidence-citations、phase15-answer-evidence、phase16-structured-answer、phase17-answer-qualification、phase18-answer-quality-operations。改动 ACL 语义时必须先跑这套脚本，尤其 phase11 与 phase12——它们盯的正是“列表/计数/引用里漏出无权限对象”这类隐蔽越权。
