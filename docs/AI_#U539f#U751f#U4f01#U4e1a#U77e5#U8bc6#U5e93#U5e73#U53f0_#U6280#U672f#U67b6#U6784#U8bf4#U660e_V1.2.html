1. 产品定位

传统知识库解决“把文档搜出来”，本平台解决“把企业数据持续加工成可信、可追溯、可治理、可推理、可引用的知识，并由统一智能检索引擎按问题动态组织答案”。
01

从“文档”升级为“知识”

文档不直接等于知识。平台将原始资料加工为证据、断言、实体、关系、知识卡片等结构化知识对象。

02

从“单一向量检索”升级为“智能检索编排”

根据问题类型，在全文、向量、知识卡片、断言、知识图谱等检索方式之间动态选择和融合。

03

从“模型依赖”升级为“平台控制”

大语言模型、向量模型、重排序模型、向量库和图数据库均可替换；真正核心能力掌握在平台治理和编排层。

2. 产品结构设计与设计层次

结构调整说明（相对“总体技术架构”版的变化与理由）

  • 接口服务独立成层：接口服务的服务对象并不只是前端界面，业务系统、AI Agent、第三方应用都通过它使用平台。把它从业务应用层提取为纵向贯通的独立层，才能准确表达“一套契约服务所有层、所有使用方”，也避免把开放能力误解为某个页面功能。
  • “知识管理”拆为三域：原“知识管理”既指抽取加工，又与来源、消费并列，概念自相包含。现按知识流转明确为知识来源 → 知识生成 → 知识消费三个子域，三者共同构成知识管理域；抽取、归一、冲突检测、裁决、发布归入知识生成，与来源接入、消费服务边界清晰。
  • 统一知识模型与治理底座分层：原区块把“知识对象”与“策略中心、追踪回放、安全合规”混装。现拆为统一知识模型（知识对象与语义资产）与企业治理底座（规则与管控能力），结构归结构、管控归管控。
  • 标准适配与可替换模型分区：把“适配契约”与“被适配对象”分为标准适配层与可替换模型与基础设施生态两层，前者说明“用什么契约接入”，后者说明“能换成什么”，回答“是否被厂商绑定”时一目了然。

3. 自研核心与能力边界

3.1 平台定位与能力边界

本平台定位为企业级“知识操作系统”，不是“文档上传 + 向量搜索 + 大模型问答”的工具组合，而是一套知识生命周期方法论的产品化落地：把企业内外部数据，经过“收集 → 接入 → 解析清洗 → 抽取归一 → 冲突检测与裁决 → 版本发布 → 生命周期治理 → 检索消费 → 反馈优化”的闭环，沉淀为可管理、可追溯、可复用的知识资产。

能力边界：平台负责知识从“产生”到“消费”的全流程能力——知识来源接入与采集治理、知识标准化（OKF）与加工治理、知识组织与本体建模（OWL）、检索编排与答案生成；并向业务系统开放知识体系生成与消费的解决方案与接口（RESTful API、MCP Server、SSE 流式、消息订阅，概念见 3.4 备注）。平台不替代底层大模型、向量库、图数据库和全文检索，而是通过标准适配层把它们纳入统一编排与治理，因此模型与存储可替换，知识资产与业务流程不推倒重来。

为业务提供的价值：不同业务线（研发、客服、营销、风控、运营、管理层决策等）无需自建知识管道，只需定义自己的知识范围、本体结构与权限策略，即可复用平台获得“本业务的知识体系生成能力”与“多形态的知识消费能力”（问答、推荐、订阅推送、图谱浏览、接口调用），实现一套底座支撑多业务知识场景。

3.2 六大核心能力

① 统一知识模型

核心不是 Chunk，而是证据、断言、知识卡片、实体、关系及其版本、状态、条件与来源——支撑冲突检测、可追溯、可审核与知识演进。（见 3.4 备注①）

② 知识来源管理

多源接入与采集治理：数据收集、情报采集、API / 文件 / 数据库 / 网页接入、解析与清洗、定时同步、变更监测。关键是接得进来、管得住、跟得上变化。

③ 知识生成

以 OKF 统一知识格式与本体（OWL）驱动加工与治理：抽取、归一、语义合并、冲突检测、裁决、审核、版本发布、生命周期管理；与知识来源、知识消费共同构成平台的知识管理域。（见 3.4 备注②③）

④ 知识消费

查询路由与多路检索编排：先判断问题类型，再动态组合全文、向量、知识卡片、断言、图谱、多跳等策略，完成融合、重排、上下文装配与证据引用。

⑤ 开放接口与业务赋能

对外提供知识体系生成与知识消费两类能力（生成侧：来源注册、OKF 导入、本体定义、任务编排；消费侧：问答、检索、推荐、订阅推送、链路回放），形态为 RESTful / MCP Server / SSE，并可封装为 Agent Skill。（见 3.4 备注④⑤⑥）

⑥ 企业级治理与可观测

权限继承、数据隔离、版本、审计、来源引用、策略配置、模型调用记录、查询链路追踪、回放与质量评估，统一纳入平台控制。

3.3 核心算法：可控程度与可换程度

知识处理链路上的算法分为三类：平台自研且不可替代（决定知识语义与治理结果）、算法实现可替换（只换引擎或模型，不改变标准与效果口径）、硬约束不可绕过（安全与合规机制）。客户可据此判断“哪些能自己换、哪些必须由平台保证”。

解析 / OCR / 版面还原原始文档转可处理文本中强控制：解析策略、质量评分、失败回退由平台编排引擎可换（Tika / MinerU / docling / PaddleOCR 等）只影响解析质量与吞吐，不影响知识语义
权限过滤与密级校验召回前过滤、输出前二次校验硬约束：由平台强制执行不可替换、不可绕过任何模型与检索引擎接入都必须经过该环节
质量评估与反馈回流覆盖度 / 新鲜度 / 一致率 / 引用率度量，反馈转工单自研·强控制：指标定义与评测集自研评测工具可换（RAGAS / 自研评测集）指标口径不变
一句话判断标准：① 标准与语义在我——OKF、本体、裁决口径、装配与引用机制不可换，换了就等于换掉知识底座；② 实现与引擎可换——模型、推理机、规则引擎、解析器、向量库、图库都通过适配器替换，替换动作是“换实现 + 跑回归评测”，不影响知识资产与业务流程；③ 硬约束不可绕过——权限过滤、密级校验、审计留痕对所有接入组件一视同仁，是平台对客户的安全承诺。

3.4 概念备注

  • ① 知识对象模型：平台对知识的最小管理单元不是文本切片（Chunk），而是证据（Evidence）——来自原始资料的原文片段与出处；断言（Claim）——可被判断真伪的结论性陈述，带条件与适用范围；知识卡片（Knowledge Card）——面向场景的结构化标准答案（如 SOP、故障处理）；实体（Entity）与关系（Relation）——构成知识图谱的节点与边。它们统一携带版本、状态、生效条件与来源，因此可被审核、冲突检测、引用、更新与退役。
  • ② OKF（Open Knowledge Format，开放知识格式）：平台自研的“知识中间语言”。无论来源是 PDF、Word、表格、网页、数据库记录还是第三方 API，进入知识管理环节后都归一为同一套 OKF 结构（来源标识、元数据、正文段落、证据块、实体与关系、时效与密级标签）。它使异构知识可统一存储、治理、检索与交换，新增来源类型只需实现一次 OKF 转换即可全平台复用。
  • ③ 本体论（Ontology）与 OWL：用 OWL / RDFS 定义类（Class）、对象属性（Object Property）、数据属性（Data Property）以及层级与约束（subClassOf、domain / range、基数与取值约束），形成企业统一的概念体系与语义关系，支持分类推理、关系补全、一致性校验与跨源语义对齐；配合推理机（Reasoner）可自动发现隐含关系与分类冲突，使知识不只是被存储，而是可被机器理解与推理。本体资产与建模规则由平台自研掌控，推理引擎可替换。
  • ④ RESTful：基于 HTTP 标准动词（GET / POST / PUT / DELETE）与资源路径的通用接口风格，用于业务系统与传统中台集成，配合 OpenAPI 描述契约与版本。
  • ⑤ MCP Server / MCP Client：MCP（Model Context Protocol，模型上下文协议）采用客户端-服务器模型。平台对外把知识能力封装为 Tools / Resources / Prompts，以 MCP Server 形态供外部 AI 助手、IDE、Agent（作为 MCP Client）直接接入；平台对内可作为 MCP Client 调用外部 MCP 工具，该能力位于标准适配层，两者不可混用。
  • ⑥ SSE（Server-Sent Events，服务端推送事件）：基于 HTTP 的单向“服务器 → 客户端”持续推送协议。客户端发起一次请求（Accept: text/event-stream）后连接保持打开，服务端可连续下发数据分片，用于问答逐字（流式）输出、任务进度推送、知识订阅通知。较 WebSocket 更轻量、天然兼容 HTTP 网关与既有鉴权、可自动重连；局限是仅支持单向，需双向实时交互时应改用 WebSocket。

4. 为什么比传统 RAG 更先进

1

知识不是“切片”，而是可治理对象

传统 RAG 以文本切片为中心；本平台以证据、断言、知识卡片、实体和关系为中心，使知识可以被审核、更新、冲突检测、引用和退役。

2

不是只有向量检索，而是多路智能检索

向量适合语义相似，BM25 适合错误码和配置项，图谱适合关系和多跳问题，断言适合规则与条件问题，知识卡片适合 SOP 和标准答案。平台按问题动态组合。

3

不是“LLM 决定一切”，而是模型受平台治理

模型只是能力组件之一。平台控制数据、知识、权限、策略、证据、检索、提示词、上下文、审核和审计，避免被单一模型绑定。

4

支持 GraphRAG 与多跳关系检索，但不被某一种实现绑定

可借鉴 GraphRAG 的实体关系、社区摘要、局部/全局检索，也可引入图传播、多跳检索等算法，但这些都通过平台算法策略层统一编排。

5

真正面向企业知识生命周期

知识不仅“能搜”，还要有来源、有版本、有生效范围、有失效机制、有权限、有审计、有反馈、有更新任务，这些决定了系统能否长期运营。

7. 产品性能评估

本节回答一个具体问题：V1.1 一套系统能承载什么数量级的知识、需要什么配置的服务器，并给出实测依据与逐组件资源占用。模型服务（LLM / Embedding / Rerank）由客户自备、独立部署，不计入本节的服务器配置结论。

7.1 评估口径与前提

计入范围：平台组件（frontend / backend / ai-service）+ 数据组件（MySQL、Redis、Elasticsearch、Milvus、Neo4j）+ 可观测（Prometheus、Grafana）。
不计入范围：LLM、Embedding、Rerank 等模型服务（Ollama 或 OpenAI 兼容网关），其算力、显存与并发单独评估，不随交付包提供。
换算假设：文档平均 8–10 页（约 8 千字），按 500 字/切片，即 1 份文档 ≈ 20 个 ContentUnit；1 个 ContentUnit ≈ 1 条向量（768 维 fp32 约 3 KB，含索引开销按 4–6 KB/条）；图谱按每份文档 20–50 个三元组；存储为 NVMe SSD；网络与网关耗时另计。
水位要求：CPU ≤ 60%、内存 ≤ 70%，保留 ≥ 30% 余量用于峰值访问与索引重建双写；容量按 10K → 100K → 500K → 1M 阶梯逐级实测，只有在延迟、召回、错误率、资源水位同时合格后才外推下一档，不以单线程结果定容。

一句话版

“我们的平台不是传统的‘文档上传 + 向量搜索 + 大模型问答’。它首先把企业数据加工成有来源、有版本、有证据、有关系的正式知识，然后通过查询理解和检索路由，根据不同问题动态选择全文、向量、知识卡片、断言和知识图谱等多种检索方式。底层大模型、向量库和图数据库都可以替换，真正掌控在平台手里的，是知识治理、检索编排、权限安全和知识生命周期。”

详细版

“从产品结构看，我们分为七层。最上面是业务应用；中间是我们的核心控制层，按知识流转分为三段：知识来源管理负责数据收集、情报采集、API/文件/数据库接入与解析清洗；知识生成负责把原始资料转成证据、断言、知识卡片、实体关系，并完成冲突检测、裁决、版本和生命周期管理；知识消费负责把用户问题经过理解、改写、路由、多路召回、融合、重排和上下文装配，再交给模型生成，同时通过知识地图、知识推荐和订阅推送主动组织与触达知识。再往下是标准适配层，大模型、向量库、图数据库、全文检索、数据连接器都通过统一接口接入，所以能够支持私有化、国产化或客户指定技术栈。我们的壁垒不依赖某一家模型厂商，而是掌握知识模型、知识治理、检索策略和企业级控制能力。”

10. 客户关注点映射

客户常见关注点对应技术设计产品价值
“模型以后升级怎么办？”模型适配器 + 多模型路由不绑定单一模型，可平滑升级或切换
“知识回答怎么保证可信？”证据、断言、知识裁决、引用、版本知识可追溯、可审核，不只是模型生成
“知识冲突和过期怎么办？”冲突检测、有效期、SUPERSEDE、知识退役支持持续治理和知识生命周期
“复杂关系问题能不能问？”知识图谱 + GraphRAG + 多跳检索支持跨文档、跨实体关系推理
“现有系统能不能接？”Connector SDK + API + 数据连接器可接 OA、Jira、数据库、文件、Wiki 等
“权限会不会泄漏？”源数据权限继承 + 检索前过滤 + 引用权限校验知识使用遵循企业权限边界
“能不能私有化？”本地模型 + 私有部署 + 存储适配适合高安全行业和内网环境
“出了问题怎么排查？”Query Trace + Prompt/模型/召回/重排记录每次问答可追踪、可回放、可评估
“知识量大，入库要多久、需要什么配置？”分级抽取 + 分片并行 + 规模档位配置建议（见第 7 节）可按知识量选型，入库与检索性能可预期、可验收
“算法以后想换成自己的行不行？”标准适配层：模型 / 推理机 / 解析器 / 向量库 / 图库可换，OKF、本体与治理口径不可换（见 3.3）客户可自主替换实现，平台保证知识资产与治理不被破坏
